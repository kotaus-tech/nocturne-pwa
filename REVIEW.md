## 2. Архитектура

### 2.1 Слои

```
UI (React 19 + framer-motion + Tailwind 4)
   ↓ useLiveQuery (dexie-react-hooks)
Данные (Dexie / IndexedDB + KV)
   ↓
Сервисы (apiClient, promptBuilder, metaParser, memoryEngine, group*, globalSearch)
   ↓ fetch / SSE
Провайдер модели (OpenAI-совместимый / Ollama / Gemini) или резервный прокси
```

Навигация — **не роутер**: `App.tsx` держит `tab: TabKey` и `activeSessionId` в
`useState`, экраны переключаются условиями. Deep-link, история браузера и
«назад» кнопкой отсутствуют (это же отмечено как ⏸ C4 в `AUDIT.md`).

### 2.2 Данные (`src/db.ts`, `src/types.ts`)

* Dexie, единственная схема **version(1)**, без миграций:
  `characters (id, name, createdAt)`, `sessions (id, characterId, createdAt, updatedAt)`,
  `messages (id, sessionId, timestamp)`, `kv (key)`.
* Все новые поля (групповая сцена, персоны, `liveScene`, `returned/left`)
  добавлены как **опциональные** — совместимость держится не миграциями, а
  санитайзерами при чтении/импорте. Решение рабочее, но хрупкое: любое новое
  поле обязано быть опциональным и «санитайзимым».
* KV-таблица хранит: `apiConfig`, `apiPresets`, `personas`, `activePersonaId`,
  `userProfile` (legacy), `nocturne_prompt_studio_v1`.
* Сильная сторона — ** defensive-нормализация**: `sanitizeCharacter`,
  `sanitizeSession`, `sanitizeMessage`, `sanitizeStats` (включая защиту от
  `NaN` в индексах — комментарий в коде прямо описывает баг «исчезающих
  персонажей»), `sanitizeCharacterIds`, `sanitizeActiveCharacterIds`,
  `sanitizeAbsentReasons`, `sanitizeSceneRelations`.
* Персоны: `getPersonaState()` читает оба KV-ключа напрямую — обход известной
  ловушки Dexie, когда чтение после `await` вложенного хелпера выпадает из
  подписки `liveQuery`. Это аккуратно задокументировано в коде и покрыто тестом
  на `fake-indexeddb`.
* Бэкап: `exportBackup()` → один JSON v2 (`characters`, `sessions`, `messages`,
  `kv`); `importBackup()` — полная перезапись четырёх таблиц в одной транзакции.

### 2.4 PWA и деплой

* `public/sw.js` (184 строки): precache оболочки, network-first для навигации,
  SWR для статики, обход `/api/` и `/.netlify/`, не активируется сам — ждёт
  команды `SKIP_WAITING` из баннера обновления. Грамотно.
* `netlify/edge-functions/llm-proxy.ts` + `netlify.toml` — резервный канал для
  провайдеров с CORS (allow-list: `api.ru-openrouter.ru`).
* `vite.config.ts` поднимает **того же** прокси мидлварой в dev — локальная
  разработка эквивалентна продакшену. Отдельно: `server.allowedHosts: true`,
  что позволяет открывать dev-сервер с любого preview-хоста.
* Сборка — `vite-plugin-singlefile`: весь бандл в одном `index.html`.
  Плюс: установка с одного файла, офлайн из коробки. Минус: нет
  переиспользования кэша между версиями (⏸ C3).

## 3. Ключевой сценарий: путь одной реплики

```
InputBar.send(text)
  → db.messages.add(userMessage)                       // реплика игрока
  → ChatView.callModelAndAppend(full, false, [target]) // полный контекст ветки
      ├─ проверка baseUrl / apiKey
      ├─ AbortController (кнопка «Стоп», сброс при выходе из чата)
      ├─ выбор говорящего:
      │    • одиночная ветка    → character
      │    • группа + адресат  → выбранный игроком герой
      │    • группа            → chooseSpeaker()  ← доп. запрос к модели
      ├─ getSliceForContext()  → окно контекста (+ ступенчатое окно)
      ├─ buildSystemPrompt()   → слоёный системный промпт (+ блоки группы)
      ├─ messagesToTurns()     → чужие реплики подписываются «Имя: …»
      └─ requestRoleplayReply()→ callLLM() → SSE → onChunk → parseMetaBlock()
  → applySceneChanges()   // returned / left: герой сам входит и выходит из кадра
  → applyRelationUpdates()// связи внутри группы обновились
  → db.messages.add(assistantMessage) + обновление шкал (currentStats | participantStats)
  → checkMilestone()      // тост о переломном моменте
  → каждые 8 реплик: compressMemory() → extractMemoriesAndDiary()
```

Важные детали реализации:

* **Стриминг** пишется в состояние `liveStreamedText` самого `ChatView`.
* **Память не теряется**: при выходе из ветки, если накопилось ≥ 4 необработанных
  реплик, `compressMemory()` дожимается в cleanup-эффекте.
* **Отмена** обрабатывается как не-ошибка (`isAbortError`), частичный ответ не
  сохраняется.
* **Окно контекста** (`contextWindow`, по умолчанию 24) считается в
  **сообщениях**, а `maxTokens` — в токенах; семантика поля в настройках
  путает (⏸ C8).

## 4. Групповая сцена — как устроена

Это самая свежая и самая сложная подсистема (~1 500 строк вместе с тестами).

| Слой | Механизм |
|---|---|
| Данные | `session.isGroup / characterIds / activeCharacterIds / absentReasons / relations / participantStats / liveScene`; `message.characterId + characterName` |
| Лидер | `session.characterId` — первый герой состава; его шкалы в `currentStats` |
| Присутствие | `resolvePresence()`; тумблер в панели режиссёра, мини-бар «N/M» в шапке |
| Выбор говорящего | `chooseSpeaker()` (короткий запрос) → при сбое `findMentionedCharacter()` → не тот, кто говорил только что → первый в сцене |
| Ручной выбор | чипы «Ответит» над строкой ввода; кнопка Play у участника |
| Ход по кругу | «Продолжить» → `nextSpeaker()` |
| Живая сцена | модель добавляет 1–2 реакции остальных в той же реплике (`liveScene`) |
| Вход/выход из кадра | модель пишет `returned` / `left` в мета-блоке, чат применяет и показывает тост |
| Связи | `mergeSceneRelations()` с лимитом 12 строк, помечает обновлённые |
| Сбой на середине | «Повторить запрос» дожимает только `pendingSpeakers()` |

Осознанная цена: **два обращения к модели за ход** в группе (роутер + ответ),
одно — при ручном выборе адресата.
