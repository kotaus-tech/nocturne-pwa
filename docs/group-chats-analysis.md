## 1. Обзор архитектуры и карта файлов

Групповой чат — это обычная ветка (`ChatSession`), в которой кроме основного
персонажа (лидера) есть 1–3 дополнительных участника. Ключевой принцип:
**за один ход отвечает ровно один персонаж**, которого выбирает либо игрок,
либо лёгкий запрос «роутера», либо эвристика. Остальные участники остаются
в сцене, видны в контексте и могут быть подписаны в чужих репликах.

| Файл | Роль |
|---|---|
| `src/types.ts` | Типы: `ChatSession` (групповые поля), `SceneRelation`, `Message.characterId/characterName` |
| `src/utils/sessionActions.ts` | `createGroupSession`, `createSession`, `cloneSession`, `deleteCharacterCascade`, `rewindToMessage` |
| `src/services/groupScene.ts` | Ядро сцены: состав, присутствие, говорящие, порядок, матчинг возвратов/уходов, связи |
| `src/services/groupRouter.ts` | Роутер: промпт выбора говорящего, парсинг ответа, `chooseSpeaker` |
| `src/services/promptBuilder.ts` | Системный промпт: блоки групповой сцены, присутствия, связей, живой сцены |
| `src/services/metaParser.ts` | Мета-протокол: `returned`, `left`, `relations` (+ thought/stats/feeling) |
| `src/services/characterGenerator.ts` | AI-генератор группы (`generateAiGroup` и fallback «по одному») |
| `src/components/characters/CharactersPage.tsx` | Точка входа: кнопка «Групповая сцена» |

| `src/components/chat/ChatView.tsx` | Оркестрация хода: `callModelAndAppend`, присутствие, цели, «Продолжить», перегенерация |

## 2. Модель данных

### 2.1 Поля `ChatSession` (`src/types.ts`)

| Поле | Тип | Назначение |
|---|---|---|
| `characterId` | `string` | **Лидер** сцены — основной персонаж ветки. Всегда первый в составе. Его шкалы живут в `currentStats` |
| `isGroup` | `boolean?` | Флаг групповой ветки. Пересчитывается при изменении состава (`characterIds.length > 0`); обнуляется при очистке сцены |
| `characterIds` | `string[]?` | ID **дополнительных** участников (без лидера). Порядок массива = очередь ходов |
| `participantStats` | `Record<string, RelationshipStats>?` | Индивидуальные шкалы отношений каждого доп. участника к игроку (лидер — отдельно в `currentStats`) |
| `activeCharacterIds` | `string[]?` | Кто сейчас **физически в сцене**. `undefined` = все присутствуют. Порядок повторяет порядок состава |
| `absentReasons` | `Record<string, string>?` | Причина «за кадром» для каждого отсутствующего (≤120 символов), уходит в промпт |
| `relations` | `SceneRelation[]?` | Микро-связи внутри группы (см. §10) |
| `liveScene` | `boolean?` | «Живая сцена». `undefined` трактуется как **включено** (проверки везде `!== false`) |

### 2.2 `SceneRelation`

```ts
interface SceneRelation {
  id: string;            // стабильный id строки
  from: string;          // id персонажа «кто относится»
  to?: string;           // id персонажа «к кому»; отсутствует = «вся группа»
  text: string;          // текст связи (≤400 символов)
  updatedAt?: number;    // если связь обновлена моделью по ходу сцены
}
```

### 2.3 `Message` — привязка реплики к автору

Каждая реплика ассистента в групповой сцене несёт:

- `characterId?: string` — ID автора (в одиночных ветках не ставится);
- `characterName?: string` — **снимок имени** на момент реплики. Это страховка:
  если персонажа потом удалят из библиотеки, пузырь всё равно покажет, кто говорил
  (`resolveSpeakerName` в `groupScene.ts` сначала ищет по `characterId` в базе,
  затем падает на снимок имени).

Кроме того, у сообщения есть `statsSnapshot` и `statsDelta` — снимок и дельта
шкал **именно этого автора** (см. §15).

### 2.4 Санитайзеры БД (`src/db.ts`)

При сохранении ветки/сообщений данные чистятся: список участников освобождается
от пустых значений, дублей и самого лидера; `participantStats` нормализуются и
обрезаются по границам 0–100; присутствие чистится от чужих/дублированных id;
причины отсутствия не бывают пустыми и обрезаются по длине; связи отбрасывают
мусор (битые пары, пустой текст). Проверено тестами в `tests/group.test.ts` и
`tests/groupSpec.test.ts`.

## 3. Создание групповой сцены

### 3.1 Точка входа — `CharactersPage`

Кнопка «Групповая сцена» (иконка `Users`) в шапке страницы персонажей открывает
`GroupSceneModal`. Отдельный генератор группы вызывается изнутри модала.

### 3.2 Ручной выбор — `GroupSceneModal.tsx`

- Выбирается **2–4 персонажа** из библиотеки (кнопка «Создать» активна только при
  выбранном минимуме; константы размера живут в генераторе: `GROUP_SIZE_MIN = 2`,
  `GROUP_SIZE_MAX = 4`).
- **Первый выбранный = лидер** сцены (помечается, его нельзя переместить вниз
  списком выбора). Модал поддерживает проп `lockedId` — так сцену можно собирать
  «вокруг» конкретного персонажа (например, из карточки персонажа).
- Есть поиск по имени/описанию.
- Внутри модала — кнопка перехода к **AI-генератору группы** (для тех, у кого
  ещё нет готового состава).
- По подтверждению вызывается `createGroupSession(leader, others, options?)`.

### 3.3 AI-генератор группы — `characterGenerator.ts`

Самостоятельный контур внутри генератора персонажей (не путать с V1 и V2/DNA):

1. **`clampGroupSize(n)`** — размер группы жёстко зажимется в 2–4.
2. **`buildGroupInstruction(params)`** — инструкция для модели: пол/теги/идея
   пользователя, размер группы, требуемая JSON-схема ответа:
   - корневой объект с полем `opening` (общая сцена-завязка) и массивом
     `characters[]`;
   - у каждого персонажа: имя, описание, характер, сценарий, первое сообщение,
     `initialStats` (шкалы отношений), опционально `lorebook`;
   - открытие обязательно: именно `opening` станет первым сообщением сцены.
3. **`parseGeneratedGroup(raw)`** — терпимый разбор: принимает ключи
   `characters`/`heroes`/`cast`/`group`, массивы, словари и даже одиночный
   объект героя; вытаскивает JSON из markdown-обёрток и «болтовни» вокруг;
   чинит оборванный ответ; даёт внятные ошибки («модель ответила прозой»,
   «пустой ответ»). Если `opening` нет — сцена откроется репликой первого героя.
4. **`generateAiGroup(params)`** — основной сценарий:
   - один запрос с `maxTokens = min(6000, 2200 + size * 700)`;
   - если ответ не распарсился — **одна строгая повторная попытка** («только JSON»);
   - если и она не удалась — **fallback «по одному»**: `generateGroupOneByOne`
     генерирует героев поштучно (каждый видит уже созданных соседей как контекст),
     а общий `opening` дописывается отдельным запросом `requestGroupOpening`;
   - если в итоге героев меньше `GROUP_SIZE_MIN` — ошибка, сцена не создаётся.
5. Готовые персонажи сохраняются в библиотеку, затем `createGroupSession`
   собирает ветку (с общим опенингом, если он есть).

### 3.4 `createGroupSession(leader, others, options?)` — `sessionActions.ts`

- `rest` = дедупликация `others` + удаление лидера из списка;
- `participants = [leader, ...rest]`;
- для каждого участника из `rest` копируются его `initialStats` в
  `participantStats` (лидер берёт `currentStats = {...leader.initialStats}`);
- заголовок ветки: `Групповая сцена: Имя1, Имя2, …` (переопределяется
  `options.title`);
- **открытие сцены**:
  - если дан `opening` — одно сообщение ассистента от лица лидера с этим текстом;
  - иначе — **каждый участник** получает стартовое сообщение со своим
    `firstMessage`, временные метки расставлены вразножку, чтобы порядок был
    стабильным;
- на каждом стартовом сообщении фиксируются `characterId` + `characterName`.

## 4. Состав сцены и присутствие

### 4.1 Состав — `resolveParticipants(session, character, charactersById)`

Возвращает персонажей сцены **строго в порядке ветки**, лидер всегда первый:

- лидер берётся из карточки `character`;
- `session.characterIds` разрешаются через базу; удалённые/неизвестные/дублированные
  id молча пропускаются;
- без лидера сцена считается пустой (возвращается `[]` — дальше работает
  одиночный сценарий либо пустое состояние).

`isGroupScene` в `ChatView` выводится как `participants.length > 1`.

### 4.2 Присутствие — `resolvePresence(session, participants)`

Возвращает `{ present, absent }`:

- `activeCharacterIds === undefined` → присутствуют **все**;
- иначе `present` = участники, чьи id есть в списке, в порядке состава;
- `absent` = список `{ character, reason }`, причина берётся из `absentReasons`;
- защита: сцена не остаётся без единого героя — если по данным в сцене никого,
  все считаются присутствующими.

Присутствие в `ChatView` — `useMemo` с зависимостями от состава, строки
`activeCharacterIds` и значений причин; панель режиссёра и полоса присутствия
получают его из чата как пропы (`presentIds` и т.п.).

### 4.3 Ручное управление присутствием

**Полоса присутствия `ScenePresenceBar`** (под шапкой чата, только при составе ≥2):
пилюли с аватарами; 🟢 «в сцене» / ⚪ «за кадром», счётчик `в сцене N/M` когда
кто-то за кадром. Клик — `handleTogglePresence(target, isPresent)`.

**`handleTogglePresence` / `applyPresence` (ChatView):**

- ввод в сцену: персонаж добавляется в `activeCharacterIds` на своё место по
  порядку состава, его причина удаляется из `absentReasons`;
- вывод за кадр: если в сцене остаётся ≤1 героя — действие блокируется;
  иначе открывается мини-диалог с вопросом о причине («ушёл в гараж») —
  причина сохраняется в `absentReasons` (обрезка до 120 символов) и уходит
  в промпт; если уводимый был выбранным адресатом — выбор адресата сбрасывается.

**Панель режиссёра** даёт те же тумблеры «в сцене / за кадром» у каждого
участника (§4.4) и подсказку: «За кадром персонаж не молчит вечно: модель
вернёт его сама, когда это будет уместно по сюжету. Вручную — тумблером рядом
с именем».

### 4.4 Управление составом в панели режиссёра (`DirectorPanel.tsx`)

Секция «Групповая сцена» панели режиссёра:

- **Лидер закреплён** строкой №1 с пометкой «основной» (без кнопки удаления).
- Остальные участники — строки `ParticipantRow` (framer-motion `Reorder`):
  - перетаскивание за ручку (`GripVertical`) + стрелки «выше/ниже»
    (`moveItem` из `groupScene.ts` — чистая перестановка соседей, вне границ
    ничего не двигает);
  - переключатель «в сцене / за кадром»;
  - кнопка ▶ «Дать ход» (только если персонаж в сцене);
  - кнопка ✕ «Убрать из сцены» → `removeParticipant`: id удаляется из состава,
    его шкалы удаляются из `participantStats`.
- Подпись: «Порядок = очередь ходов. Перетаскивайте за ручку или двигайте
  стрелками».
- **Добавление**: селект свободных персонажей (все, кроме лидера и уже
  участников, по алфавиту) + кнопка «Добавить»; кнопка «Добавить избранных (N)»
  добавляет всех избранных одним нажатием.
- **«Очистить сцену»** (`clearParticipants`): обнуляет состав и заодно
  `participantStats`, `activeCharacterIds`, `absentReasons`, `relations`,
  `isGroup = false` — ветка становится одиночной.
- `updateParticipants(ids)` пишет `characterIds` и пересчитывает `isGroup`;
  при наличии `activeCharacterIds` синхронизирует присутствие: **новый участник
  сразу входит в сцену**, ушедшие из состава пропадают из списка присутствия.

## 5. Выбор говорящего (маршрутизация)

За ход отвечает **один** персонаж. Источник выбора — по убыванию приоритета:

### 5.1 Явный выбор игрока

1. **Адресат в `InputBar`**: при составе >1 над полем ввода появляется ряд
   аватаров присутствующих. Клик выбирает `targetCharacterId` (повторный клик
   снимает). При отправке `handleSend` передаёт адресата как
   `onlySpeakers = [target]`, а в запрос (не в историю!) дописывается
   невидимая реплика-подсказка:
   > `[Отвечает: Имя. Игрок обратился к нему в первую очередь — отвечай за Имя, остальные остаются в сцене.]`
2. **«Дать ход»** ▶ в панели режиссёра (`handleRequestTurn`): панель
   закрывается, ход уходит выбранному персонажу **в режиме инициативы**
   (см. §6.4), панель больше не нужна.

### 5.2 Авто-роутер — `groupRouter.ts`

Если игрок никого не назначил, выполняется лёгкий отдельный запрос «кто
отвечает первым». Он не мешает основному ответу (короткий промпт, десятки
токенов) и позволяет вступить тому, кого реплика действительно задела.

**Входные данные** (`SceneRoutingInput`): присутствующие, микро-связи группы
(≤6 первых), имя игрока, последняя реплика игрока (≤600 символов), кто отвечал
до этого (`lastSpeakerId`), заметки режиссёра (≤300 символов).

**Полный текст промпта роутера** (`buildRoutingPrompt`):

```text
Ты — режиссёр ролевой сцены с несколькими персонажами. Определи, кто из них отвечает СЕЙЧАС первым.

ПЕРСОНАЖИ В СЦЕНЕ:
- Имя (id: …): краткий профиль до 140 символов (характер → подзаголовок → описание)

ОТНОШЕНИЯ ВНУТРИ ГРУППЫ:            ← блок только если связи есть (макс. 6)
- Кто → кого: текст связи

АТМОСФЕРА СЦЕНЫ: заметки режиссёра    ← блок только если заметки есть

ПОСЛЕДНЯЯ РЕПЛИКА ИГРОКА (Имя): «текст»

КАК ВЫБИРАТЬ:
1. Если игрок обратился к кому-то по имени — отвечает он.
2. Иначе — тот, кого эта реплика задела сильнее всех по характеру и отношениям.
3. Не отдавай ход тому, кто только что говорил, если есть другие кандидаты.
4. Если реплика обращена ко всем — отвечает самый активный или самый заинтересованный.

Ответь СТРОГО одной строкой, без пояснений:
[Отвечает: Имя]
```

Вызов идёт через `callLLM` с историей из одной «реплики» `[Кто отвечает первым?]`.

**Парсинг ответа** (`parseRoutingAnswer`): три формы —
`[Отвечает: Имя]`, `Отвечает: Имя` (свободная строка), `<speaker>Имя</speaker>`;
поиск сначала точного совпадения имени (сравнение в нижнем регистре `ru-RU`),
затем частичного (имя длиной >2, как начало/подстрока ответа), и последний
фолбэк — `findMentionedCharacter` (любое упоминание имени в тексте).

### 5.3 Полная цепочка `chooseSpeaker`

```text
1. роутер (запрос к модели)
2. при сбое/невнятном ответе: упоминавшийся в реплике игрока герой
3. иначе: первый из присутствующих, кроме только что говорившего (анти-повтор)
4. иначе: первый присутствующий
```

Ошибки роутера глотаются намеренно: «сбой роутера — не повод не ответить игроку».

### 5.4 «Продолжить» — `nextSpeaker`

В группе кнопка «Продолжить» передаёт ход **следующему по кругу**
(`nextSpeaker(present, lastSpeakerId)`): круговая ротация от последнего
говорившего, чтобы следующий герой отреагировал на услышанное, а не повторял
предыдущего. Вызов идёт в режиме продолжения сцены одним говорящим. В одиночной
ветке «Продолжить» отвечает тот же персонаж, также получая инструкцию продолжить
последний момент, а не сообщение о молчании игрока.

### 5.5 Прерванный ход — `pendingSpeakers` + «Повторить»

`handleRetry`: если последнее сообщение — пользовательское, просто повторяем
запрос. Если ход группы оборвался на середине (кто-то уже ответил, кто-то нет),
`pendingSpeakers(full, participants, leaderId)` вычисляет тех, кто ещё **не
ответил на последнюю реплику игрока**, и «Повторить» дожимает только их
(`onlySpeakers = pending`). Если ответили все — дожимать некого, ничего не
происходит.

## 6. Механика группового хода

### 6.1 `callModelAndAppend(contextMessages, isInitiative, onlySpeakers?, targetName?)`

Единая точка генерации ответа. Шаги для группы:

1. **Определение говорящих**: `onlySpeakers` (явное назначение) → иначе
   `chooseSpeaker` (§5.3) по пулу присутствующих (если присутствие пустое — по
   всему составу). В одиночной ветке — как раньше, `[character]`.
2. **Цикл по говорящим** (в группе после роутера обычно один, но «дожим»
   прерванного хода может идти списком):
   - `workingContext` — скользящее окно контекста (`getSliceForContext` с
     учётом `contextWindow` и ступенчатого режима); **после каждой готовой
     реплики новое сообщение добавляется в `workingContext`**, т.е. каждый
     следующий участник видит уже сказанное предыдущими;
   - **свои шкалы**: `statsFor(speaker.id)` — лидер берёт `session.currentStats`,
     остальные — `participantStats[id]`, а при их отсутствии — `initialStats`
     карточки (никогда не чужие шкалы);
   - **системный промпт** строится от лица говорящего с групповым контекстом
     `{ others: остальные присутствующие, currentStats: шкалы говорящего,
     absent: за кадром с причинами, relations: связи }` (§7);
   - **история превращается в turns** с подписью чужих реплик:
     `messagesToTurns(recent, turnLabelFor(speaker.id))`. `buildAssistantLabeler`
     создаёт функцию-подпись: реплики **других** персонажей получают префикс
     `Имя: …`, собственные реплики говорящего остаются без подписи (модель
     понимает, где «её» слова). Пустое имя подписью не становится;
   - ручное продолжение сцены или ручная инициатива добавляют разные скрытые управляющие инструкции (см. §6.4);
   - `requestRoleplayReply` со стримингом (`streamingCharacterId` управляет
     аватаром «печатает…»);
   - после ответа — применения сцены (§9, §10) и запись сообщения.
3. **Запись реплики**: `Message` с `characterId`/`characterName` автора,
   `statsSnapshot`, `statsDelta` (§15), `innerThought`. Шкалы говорящего
   сохраняются: у лидера — в `session.currentStats`, у остальных — в
   `participantStats`.
4. Тосты: `feelingHint` в группе подписывается именем (`Имя: Тепло и надежда`);
   вето-проверки на показ тостов — `session.showRelationshipToasts !== false`.
5. Счётчик памяти: каждые `MEMORY_EXTRACT_INTERVAL` сообщений — фоновая
   экстракция (§13).

### 6.2 Перегенерация (`handleRegenerate`)

Реплика переписывается **тем же персонажем, что её написал**
(`speakerFor(message)`): свои шкалы, свой групповой промпт, подписанный
контекст. Новый вариант добавляется в `swipes`. Перегенерация тоже двигает
сцену — применяет `returned`/`left` и обновления связей.

### 6.3 Повторная отправка (`handleSend`)

Сохраняет сообщение игрока, сбрасывает адресата и вызывает
`callModelAndAppend` — с `onlySpeakers=[target]` и `targetName`, если адресат
был выбран аватаром.

### 6.4 Ручное продолжение и инициатива (скрытые управляющие инструкции)

Кнопка **«Продолжить»** не является сообщением игрока и не означает, что
игрок молчит. В конец истории добавляется отдельная техническая инструкция:

> `[Продолжение текущей сцены. Это техническая команда интерфейса, а не реплика игрока; продолжи происходящее непосредственно с последнего момента в новом сообщении, без повтора и пересказа уже выданного текста. Не начинай сцену заново и не говори, не думай и не действуй за игрока.]`

Для отдельной команды **«Дать ход»** сохраняется другой режим — сознательная
инициатива персонажа без реплики игрока:

> `[{Имя игрока} молчит или выжидает. {Имя героя}, прояви собственную инициативу: продолжи мысль, соверши физическое действие, измени положение, начни новую реплику или нарушь паузу. НЕ говори и НЕ действуй за {имя игрока}!]`

## 7. Промпты групповой сцены (полные тексты)

Все блоки собирает `buildSystemPrompt` (`promptBuilder.ts`) и добавляет их
**только при наличии группового контекста**. Одиночные ветки не получают ни
одного из этих блоков — их промпт не меняется.

### 7.1 Блок «ГРУППОВАЯ СЦЕНА: НЕСКОЛЬКО ПЕРСОНАЖЕЙ»

Добавляется, когда есть хотя бы один другой присутствующий. Состав: ростер
остальных с краткой выжимкой (характер → описание → подзаголовок, до 160
символов) и правила. Полный текст:

```text
### ГРУППОВАЯ СЦЕНА: НЕСКОЛЬКО ПЕРСОНАЖЕЙ
Сейчас в сцене несколько персонажей. Ты отыгрываешь ТОЛЬКО {имя говорящего}.
Кто ещё здесь (их реплики приходят отдельными сообщениями истории):
- {Имя}: {краткая выжимка}
Правила групповой сцены:
1. Реагируй на других персонажей как на живых людей: услышь их, смотри, перебивай, соглашайся, спорь, подмечай их реакцию — но НИКОГДА не пиши за них и не придумывай им реплики, мысли или действия.
2. Не отвечай за {имя игрока}: ход игрока приходит отдельным сообщением.
3. Не подписывай свою реплику именем и не добавляй заголовков вида «{имя}:» — пиши сразу текст отыгрыша.
4. Не пересказывай чужие реплики и не подводи итоги диалога: веди только свой ход и свою часть сцены.
5. ПРАВИЛО ТРЕУГОЛЬНИКА (анти-вытеснение игрока): между персонажами кипит своё — спор, подколки, взгляды, старые обиды. Но {игрок} всегда якорь сцены: обращайся к нему за мнением, лови его реакцию, апеллируй к нему как к свидетелю или судье спора. {игрок} не должен оставаться пассивным зрителем чужого разговора.
6. ЖИВАЯ СЦЕНА: …            ← только если включена «живая сцена» (§11)
```

Смысловые акценты: правило 1 запрещает «марионеточность» (писать за других),
правило 3 борется с двойной подписью (имя уже добавляет интерфейс), правило 5
защищает игрока от вытеснения в зрители чужого диалога.

### 7.2 Блок «СЦЕНИЧЕСКОЕ ПРИСУТСТВИЕ»

Добавляется, когда кто-то за кадром (`group.absent` не пуст). Полный текст:

```text
### СЦЕНИЧЕСКОЕ ПРИСУТСТВИЕ
В сцене сейчас: {имена присутствующих}.
За кадром (их сейчас нет в локации) — не говори за них и не действуй от их имени, даже если история помнит их реплики:
- {Имя} — {причина}
ВОЗВРАЩЕНИЕ В СЦЕНУ: если по времени и сюжету кто-то из них возвращается — опиши его появление (шаги, голос, короткая реплика) и добавь в мета-блок поле "returned": ["Имя"]. Это вернёт персонажа в сцену, и дальше он снова сможет говорить.
Персонаж возвращается сам, когда это уместно по сюжету, — не жди игрока: если он ушёл в магазин, рано или поздно он вернётся. Но если он вышел только что — не торопи возвращение.
УХОД ИЗ СЦЕНЫ: если по ходу ответа герой сам уходит (по делам, позвонили, вышел покурить, уехал) — опиши уход и добавь в мета-блок поле "left": {"Имя": "короткая причина"}. Уходит только тот, у кого есть причина: не уводи героев просто так и никогда не уводи всех сразу — сцена не должна опустеть.
```

### 7.3 Блок «ВЗАИМООТНОШЕНИЯ ВНУТРИ ГРУППЫ (КАТАЛИЗАТОР СЦЕНЫ)»

Добавляется при наличии связей. Связи рендерятся через имена: `Кто → кого: текст`
(неизвестный id → «Кто-то»/«кто-то из группы», связь без `to` → «вся группа»).
Полный текст инструкции под списком:

```text
Отыгрывай эти отношения через подтекст, интонации, взгляды и мелкие детали: не пересказывай их словами, показывай в поведении.
Если по ходу ответа отношение кого-то из героев к другому правда изменилось (обиделся, потеплел, начал ревновать) — добавь в мета-блок поле "relations": [{"from": "Имя", "to": "Имя", "text": "как теперь относится"}]. Обновляй только то, что действительно поменялось: если всё как было — поля не пиши.
```

### 7.4 Локальный мета-протокол: групповые правила 5–7

Для локальных моделей мета-протокол теговый (`<thought>`/`<stats/>` в начале
ответа). В групповой сцене **и только если кто-то за кадром** к правилам 1–4
дописываются:

```text
5. Если в этой реплике персонаж, который был за кадром, возвращается в сцену — добавь рядом с <stats .../> тег <returned names="Имя" />.
6. Если герой сам уходит из сцены по ходу ответа — добавь тег <left names="Имя" reason="короткая причина" />. Всех сразу не уводи.
7. Если отношение между героями изменилось — добавь тег <relation from="Имя" to="Имя" text="как теперь относится" />.
```

### 7.5 Шкалы состояния

Строка «ТЕКУЩЕЕ СОСТОЯНИЕ ОТНОШЕНИЙ» в группе берёт
`group.currentStats` — **шкалы именно говорящего**, а не `session.currentStats`.
Формат тот же, что в одиночных чатах (доверие/привязанность/близость/
напряжение/конфликт, опционально влечение у V2-персонажей, статус).

### 7.6 Что из общих блоков действует и в группе

Заметки режиссёра («РЕЖИССЁРСКИЙ КОНТЕКСТ И НАСТРОЕНИЕ СЦЕНЫ») подмешиваются
каждому говорящему и учитываются роутером; синопсис, факты памяти, активированный
лоребук и директива скрытой мысли — общие, как в одиночном чате. Память ведётся
**от лица основного персонажа** (лидера ветки), но с пометкой о составе (§13).

## 8. Мета-протокол: returned / left / relations

### 8.1 Облачные модели — JSON-блок в конце ответа

Инструкция `META_PROTOCOL_INSTRUCTION` требует в конце ответа блок ```` ```meta ````
с полями `innerThought`, `feelingHint`, `stats`, а для групповых сцен —
необязательными:

```text
Необязательное поле "returned": ["Имя"] — кого из персонажей за кадром этот ответ вернул в сцену (нужно только в групповых сценах, когда кто-то был в отлучке).
Необязательное поле "relations": [{"from": "Имя", "to": "Имя", "text": "как изменилось отношение"}] — только если по ходу ответа отношение между героями правда изменилось.
Необязательное поле "left": {"Имя": "короткая причина"} — кто ушёл из сцены по ходу этого ответа (ушёл по делам, вышел, уехал). Не отправляй героев за кадр без причины и не уводи всех сразу.
```

### 8.2 Локальные модели — теги

`<returned names="Ая, Рин" />`, `<left names="Ая" reason="ушла в магазин" />`,
`<relation from=… to=… text=… />`. Теги вырезаются из текста, их содержимое
разбирается теми же нормализаторами; блок, который не удалось разобрать, даёт
`metaWarning` (уведомление в чате) и не трогает шкалы.

### 8.3 Нормализация (`metaParser.ts`)

- `parseReturnedNames` — принимает строку (в т.ч. разделители «,», «и»),
  массив или одиночное значение; отбрасывает пустые значения;
- разбор `left` — принимает и словарь `{"Имя": "причина"}`, и массив объектов,
  и строку; причина необязательна;
- разбор `relations` — список объектов `{from, to?, text}`; пары без `from`
  или с пустым `text` отбрасываются; `to` может отсутствовать (= вся группа);
- ключи-синонимы терпимы: `returned/returnedNames/returned_names/вернулся`,
  `left/leftNames/left_names/ушли`, `relations/связи`.

## 9. Динамика сцены: возвраты и уходы

Модель двигает сцену сама, а игрок — вручную; оба пути сходятся в одном
состоянии `activeCharacterIds` + `absentReasons`.

### 9.1 Сопоставление имён (`groupScene.ts`)

- **`matchReturnedCharacters(names, absent)`** — только те, кого действительно
  нет в сцене. Сначала точное совпадение имён (нижний регистр `ru`), затем
  «основа» имени (учёт падежей: «Аю», «Ае» → «Ая») — с защитой от коротких
  ложных срабатываний. Неизвестных героев не выдумываем.
- **`matchLeftCharacters(left, present)`** — только присутствующие, каждый не
  больше одного раза; причина переносится в `absentReasons` (≤120 символов).

### 9.2 Применение — `applySceneChanges` (ChatView)

Вызывается после каждой сгенерированной реплики (обычной и перегенерации),
если в распарсенном ответе есть `returned` или `left`:

1. новый список присутствующих = порядок состава ∩ (был в сцене ИЛИ вернулся)
   минус ушедшие — вернувшиеся встают на своё место в порядке состава;
2. **сцена не должна опустеть**: если уходят все — изменения не применяются;
3. причины вернувшихся удаляются, причины ушедших пишутся;
4. один `db.sessions.update` на оба изменения;
5. тосты (если не выключены): «Ая снова в сцене» / «В сцену вернулись: Ая, Рин»
   или «Имя выходит из сцены (причина)» / «За кадром: …».

Ручное присутствие (§4.3) использует тот же формат данных.

## 10. Взаимоотношения внутри группы

### 10.1 Хранение и источники

`session.relations: SceneRelation[]` (§2.2). Источники записей:

- **ручной редактор** в панели режиссёра (§10.2);
- **модель** через мета-поле `relations` — только когда отношение реально
  изменилось (§7.3, §8).

### 10.2 Редактор в панели режиссёра

Секция «Взаимоотношения в группе» (появляется при наличии участников):

- текст-пояснение: «Кто как относится к кому: спор, старая обида, тайная
  симпатия. Это топливо для живого полилога — модель играет связи через
  подтекст, а не пересказ. Если по ходу сцены кто-то обиделся или потеплел,
  связь обновится сама — такую строку можно поправить руками»;
- каждая строка: два селекта «кто думает → о ком» (вариант «вся группа» для
  пустого `to`) и текстовое поле; строки, обновлённые моделью
  (`updatedAt`), помечаются подсказкой «Обновлено по ходу сцены — можно
  поправить вручную»;
- кнопка добавления новой связи и удаление существующих.

### 10.3 Обновление моделью — `mergeSceneRelations(existing, incoming, participants)`

- имена из мета-блока сопоставляются с составом сцены (точное совпадение,
  затем основа для падежей); **неизвестные имена пропускаются** — связь не
  создаётся «на воздух»;
- если пара (`from`+`to`) уже есть — обновляется её текст и ставится
  `updatedAt`; если текст не изменился — изменения не фиксируются;
- новая пара добавляется; всего связей **не больше 12** (`MAX_SCENE_RELATIONS`),
  текст обрезается до 400 символов;
- результат: `{ relations, changed }` — список изменённых пар питает тост
  «Связи обновились: Ая → Рин» или «Связи обновились: 2 пары» (одна запись на
  несколько пар), при пустом `changed` ничего не пишется и тост не показывается.

### 10.4 Использование связей

- **роутер**: до 6 связей в промпте выбора говорящего — «кого реплика задевает»;
- **промпт каждого говорящего**: блок §7.3 («катализатор сцены»).

## 11. «Живая сцена» (liveScene)

**Суть**: отвечает по-прежнему один герой, но в конце реплики он может дать
1–2 короткие реакции остальных — сцена звучит живее. Реакции идут инлайн
(«— **Имя:** реплика»), отдельного парсера под них нет — это договорённость
промпта, а не структура данных.

**Управление**: чекбокс в панели режиссёра (виден при ≥2 участниках):

> «Живая сцена. Отвечает по-прежнему один герой, но в конце реплики он может
> дать 1–2 короткие реакции остальных — так сцена звучит живее.»

Значение пишется в `session.liveScene`; `undefined` считается включённым
(`session.liveScene !== false`).

**Условие действия**: блок правила 6 добавляется в промпт только если
`liveScene` включён **и** в сцене есть другие присутствующие. Полный текст
правила 6 (см. также §7.1):

```text
6. ЖИВАЯ СЦЕНА: если реплика задела кого-то ещё, ты можешь добавить в КОНЦЕ своего ответа 1–2 короткие реакции других присутствующих — каждую с новой строки, в формате «— **Имя:** реплика» (можно с одним коротким действием в *звёздочках*). Это единственное исключение из правила 1: реакции короткие, по одной-двум фразам, и только от тех, кто сейчас в сцене. Если реагировать некому или момент не тот — не добавляй никого.
```

При выключенной «живой сцене» правило 6 отсутствует, и правило 1 (не писать за
других) действует без исключений. Проверено тестом в `groupSpec.test.ts`.

## 12. Отрисовка и UI

### 12.1 Шапка чата

- рядом с именем лидера появляется **бейдж группы** (иконка `Users`): число
  присутствующих или `присутствуют/всего`, если кто-то за кадром;
  всплывающая подсказка перечисляет состав и «за кадром» с причинами;
- подзаголовок вместо тэглайна: «в сцене: имена остальных» (или «только вы
  двое» при составе из двух).

### 12.2 Полоса присутствия `ScenePresenceBar`

Пилюли с аватарами всего состава, клик переключает присутствие (тот же путь,
что тумблеры панели режиссёра). Скрывается при составе <2. Блокируется на
время генерации (`sending`).

### 12.3 Пузыри сообщений

- `speakerFor(message)` определяет автора реплики: по `characterId` из базы,
  иначе лидер ветки; `speakerName` — `resolveSpeakerName`: имя из базы →
  снимок `characterName` → имя лидера; реплики игрока подписываются именем
  персоны;
- в группе каждый пузырь получает аватар и имя **своего** автора
  (`MessageBubble` + `Avatar`);
- подписи авторов используются и в служебных местах: запросы предложений,
  книга-режим (`NovelReader` получает `resolveSpeakerName`), сжатие памяти.

### 12.4 Поле ввода `InputBar`

В группе над полем ввода — аватары присутствующих для выбора адресата
(клик выбирает цель, повторный клик или кнопка «любой» рядом снимает выбор;
выбранная цель подсвечивается). Пропы: `groupScene`, `participants`,
`targetId`, `onSelectTarget`. Кнопки «Продолжить», «Стоп», подсказки — как в
одиночном чате.

### 12.5 Панель режиссёра

См. §4.4 (состав/порядок/присутствие), §10.2 (связи), §11 (живая сцена).
Кроме того: «Дать ход» для лидера в закрепленной строке №1; все кнопки хода
блокируются на время генерации (`sending`).

### 12.6 Тосты

Групповые события показываются теми же `RelationshipToast` (тип `status`):
возвраты в сцену, уходы за кадр, обновления связей; эмоциональные подсказки —
с именем автора («Рин: Тепло и надежда»). Всё глушится настройкой ветки
«показывать тосты отношений».

## 13. Память в групповой сцене

Память (дневник, факты, синопсис) по-прежнему ведётся **от лица основного
персонажа ветки**, но с учётом состава — `groupCastNote(others)` в
`memoryEngine.ts` добавляет к промптам экстракции:

```text
ВАЖНО: это групповая сцена, вместе с тобой в ней были: {имена}. Учитывай их
слова и поступки: в фактах фиксируй и то, что произошло между героями, а не
только между тобой и игроком.
```

Пометка подмешивается и в фоновое извлечение (каждые `MEMORY_EXTRACT_INTERVAL`
сообщений), и в полное сжатие памяти. `othersInScene` в `ChatView` — имена всех
участников кроме лидера.

## 14. Жизненный цикл и каскады

Все операции — `sessionActions.ts` + санитайзеры БД.

### 14.1 Создание
`createGroupSession` (§3.4): состав, стартовые шкалы, открытие сцены.

### 14.2 Добавление участника «на лету»
Панель режиссёра → `updateParticipants`: новый герой сразу входит в сцену
(синхронизация `activeCharacterIds`), получает стартовые шкалы при первом
своём ходе (иначе `statsFor` возьмёт `initialStats` карточки).

### 14.3 Удаление участника из сцены
`removeParticipant`: только из состава и `participantStats`; сама карточка в
библиотеке остаётся. Реплики героя в истории сохраняют снимок имени —
пузыри продолжают показываться.

### 14.4 Очистка сцены
`clearParticipants`: состав, шкалы участников, присутствие, причины, связи и
`isGroup` обнуляются — ветка становится одиночным чатом с тем же лидером.

### 14.5 Удаление персонажа из библиотеки — `deleteCharacterCascade`
- персонаж удаляется из всех карточек;
- из **всех групповых веток** вычищается его участие: `characterIds` и
  `participantStats`; из присутствия/причин — автоматически санитайзерами;
- если удалён **лидер** ветки — ветка теряет персонажа (дальнейшая судьба
  такой ветки — как у одиночной без персонажа: она остаётся в истории с
  снимками имён в репликах).

### 14.6 Клонирование и перемотка
- `cloneSession` копирует ветку вместе с групповыми полями;
- `rewindToMessage` обрезает историю до выбранной реплики; состав, присутствие
  и связи — свойства ветки и от перемотки не меняются (осознанное решение:
  сцена «помнит» текущий состав, а история — только то, что сказано).

### 14.7 Свайпы
Переключение свайпа у групповой реплики — обычное; перегенерация пишет новый
вариант тому же автору (§6.2).

## 15. Шкалы отношений по участникам

- У каждого персонажа группы — **свои** отношения с игроком: лидер —
  `session.currentStats`, остальные — `participantStats[id]`.
- При создании ветки стартовые значения копируются из `initialStats` карточек
  (у лидера — в `currentStats`).
- Каждая реплика несёт `statsSnapshot` (шкалы автора после ответа) и
  `statsDelta` (дельта к прежнему значению) — панель аналитики отношений
  показывает динамику по авторам честно, без подмен.
- Строка состояния в системном промпте всегда берёт шкалы **говорящего**
  (§7.5); роутер шкалы не видит (оперирует связями и текстами).
- При удалении участника его шкалы удаляются из ветки; при повторном
  добавлении того же персонажа старт снова идёт от `initialStats`.

## Краткая схема группового хода (итог)

```
Игрок пишет / «Продолжить» / «Дать ход» / «Повторить»
        │
        ▼
выбор говорящего: адресат игрока → роутер (лёгкий запрос) → упоминание → ротация
        │
        ▼
системный промпт от лица говорящего:
  паспорт персонажа + ГРУППОВАЯ СЦЕНА (правила 1–6)
  + СЦЕНИЧЕСКОЕ ПРИСУТСТВИЕ + СВЯЗИ (катализатор)
  + шкалы ГОВОРЯЩЕГО + память/заметки режиссёра
        │
        ▼
история с подписанными чужими репликами → стриминг ответа
        │
        ▼
парсинг мета-блока: thought/stats/feeling (+ returned/left/relations)
        │
        ├── returned/left → applySceneChanges (состав, причины, тосты)
        ├── relations → mergeSceneRelations (связи ветки, тост)
        └── шкалы → лидер в currentStats / остальные в participantStats
        ▼
сообщение с characterId/characterName автора, снапшотом и дельтой шкал
```
