# 1. Короткий итог и главные инварианты

Групповой чат в NOCTURNE — это не отдельный «монолитный режим», а обычная
`ChatSession`, к которой добавлены состав сцены, присутствие, отдельные шкалы,
отдельные личные состояния и единая шина патчей. Благодаря этому одиночные
ветки продолжают работать старым путём, а групповые получают дополнительные
слои только тогда, когда в фактическом составе больше одного персонажа.

## 1.1. Базовая схема

```text
Игрок отправляет реплику
        │
        ├─ она сохраняется как Message с snapshot присутствия и targetCharacterId
        │
        ├─ если выбран присутствующий адресат → его ход
        ├─ если выбран отсутствующий с новым контактом → отдельный remote-thread
        └─ иначе → лёгкий router выбирает одного присутствующего героя
                │
                ▼
        для выбранного героя строятся:
        - его system prompt;
        - его шкалы отношений;
        - его private notes и intention;
        - только допустимый контекст истории
                │
                ▼
        модель отвечает один раз
                │
        ├─ meta-parser отделяет художественный текст от метаданных
        ├─ presence/relations/sceneShift/intention/stats собираются в один patch
        ├─ LiveScene-хвосты отделяются в косметические echo-сообщения
        └─ Dexie-транзакция пишет состояние и сообщения атомарно
                │
                ▼
        фоновый upkeep:
        - персональная память по dirty flag;
        - нейтральная хроника;
        - offscreen tick для отсутствующих.
```

## 1.2. Инварианты новой версии

1. **Лидер не является единственным владельцем памяти.**  У лидера и каждого
   участника есть одинаковый тип `ParticipantMemory`.
2. **Состав, присутствие и существование — разные понятия.** Персонаж может быть
   за кадром, но продолжать жить и иметь внутренние решения.
3. **Private notes не входят в общий prompt.** В обычный roleplay-запрос попадает
   только память текущего говорящего.
4. **Общая хроника не является дневником лидера.** Она строится от третьего лица
   и хранится как общий, нейтральный слой.
5. **Отсутствующий герой не становится обычным speaker.** Он может вернуться по
   сюжету или ответить дистанционно, но remote-ответ не меняет
   `activeCharacterIds`.
6. **LiveScene echo не равно полноценный ход.** Echo отображается, но не должно
   менять шкалы, router anti-repeat, relations или личную память.
7. **Новые указатели используют `message.id`, а не индекс массива.** Это делает
   перемотку и импорт безопаснее.
8. **Фоновые операции не делают blind last-write-wins.** Они читают свежую
   сессию внутри Dexie-транзакции и используют подписи заметок/намерений.
9. **Дефолт offscreen — отсутствие значимого события.** Персонаж не обязан
   постоянно производить драму.
10. **V1 и V2 не заменяют друг друга.** Старый генератор, старые карточки,
    старые API-пути и новые Character DNA сосуществуют.

# 3. Доменная модель: состав, присутствие, существование и знание

Главная концептуальная граница новой версии выглядит так:

```text
composition / cast       = кто входит в историю вообще
activeCharacterIds       = кто физически находится в текущем кадре
participantMemory        = что персонаж накопил в своём внутреннем слое
world existence          = он продолжает жить даже вне кадра
prompt visibility        = что именно разрешено показать конкретному запросу
```

## 3.1. Состав сцены

Лидер хранится в `session.characterId`. Дополнительные участники хранятся в
`session.characterIds`. Функция `resolveParticipants` всегда возвращает:

```text
[leader, ...validUniqueExtrasInSavedOrder]
```

Если карточка дополнительного героя удалена или неизвестна, она пропускается.
Старые сообщения этого героя при этом не превращаются в реплики лидера: если в
сообщении есть `characterName`, UI использует снимок имени.

## 3.2. Физическое присутствие

`activeCharacterIds` — это не состав и не память.

- `undefined` означает «все участники присутствуют»;
- пустой список после санитизации также превращается в безопасное состояние «все
  присутствуют»;
- непустой список задаёт физически присутствующих;
- отсутствующие получают причину из `absentReasons`.

`resolvePresence` возвращает:

```ts
{
  present: Character[],
  absent: { character: Character; reason?: string }[]
}
```

Ни один обычный запрос не должен говорить за героя из `absent`, даже если его
старые реплики присутствуют в истории.

## 3.3. Existence за кадром

Отсутствующий герой:

- не попадает в обычный пул router-а;
- не получает обычный ход через `Продолжить`;
- не появляется в `others` как присутствующий;
- может быть возвращён через `returned` или вручную;
- получает offscreen tick при включённой фоновой жизни;
- может инициировать SMS/звонок/пост/сообщение;
- сохраняет и меняет собственную `ParticipantMemory`.

Именно это реализует принцип **Presence ≠ Existence**.

## 3.4. Knowledge boundary

Разные источники контекста имеют разные права:

| Источник | Что ему разрешено видеть |
|---|---|
| Обычный roleplay speaker | Общую хронику, обычный недавний контекст, присутствующих героев, relations, собственные stats, собственные private notes/intention. |
| Другой присутствующий герой | Свою private memory, а не private notes соседа. |
| Router | Краткие намерения присутствующих, roster, relations, последнюю пользовательскую реплику; не private notes. |
| Offscreen tick | Причину отсутствия, собственные private notes/intention, нейтральную хронику, релевантный digest relations/stats. |
| Remote reply | Только isolated remote thread, профиль героя, его private memory; не основной group context, не director notes, не group summary/relations. |
| Director UI | Полную редакторскую прозрачность для пользователя, включая memory всех участников. |

# 4. Структура данных `ChatSession`, `ParticipantMemory` и `Message`

## 4.1. Групповые поля `ChatSession`

| Поле | Назначение и поведение |
|---|---|
| `characterId` | Лидер. Его stats остаются в `currentStats`, что сохраняет старый API и старые сохранения. |
| `isGroup` | Флаг состава. Фактический `ChatView` считает сцену групповой, когда разрешено более одного участника. |
| `characterIds` | Дополнительные участники в порядке состава и очереди ручного обхода. |
| `participantStats` | `characterId → RelationshipStats` для дополнительных участников. |
| `activeCharacterIds` | Физически присутствующие участники. `undefined` = все. |
| `absentReasons` | `characterId → reason`, максимум 120 символов после санитизации. |
| `relations` | До 12 рабочих связей через reducer; каждая связывает `from`, необязательный `to` и текст. |
| `participantMemory` | `characterId → ParticipantMemory` для лидера и всех дополнительных участников. |
| `offscreenLifeEnabled` | `false` отключает фоновые тики; отсутствие поля трактуется как включённое. |
| `offscreenTickInterval` | Интервал 4–20 ходов; дефолт resolver-а — 6. |
| `liveScene` | `false` отключает инлайн-echo; отсутствие поля трактуется как включённое. |
| `summary` | В группе используется как общая нейтральная хроника; старый смысл синопсиса сохраняется для одиночных веток. |
| `memoryExtractedCount` | Старый V1-счётчик для legacy-памяти. Новая групповая dirty-memory опирается на per-character message pointers. |
| `storyLog`, `diary`, `extractedFacts` | Старый V1-слой. В группе не является источником private notes нового контура; поля сохраняются для обратной совместимости. |

## 4.2. `ParticipantMemory`

```ts
interface ParticipantMemory {
  characterId: string;
  privateNotes: string[];
  intention: Intention | null;
  lastExtractedMessageId: string | null;
  absentSinceMessageId: string | null;
  ticksSinceLastSignificant: number;
  significantSinceLastContact: number;
  lastTickAtMessageId?: string | null;
}
```

### Лимиты и значения по умолчанию

| Параметр | Значение |
|---|---:|
| `MAX_PRIVATE_NOTES` | 5 заметок на персонажа |
| `MAX_PRIVATE_NOTE_LENGTH` | 300 символов |
| `MAX_INTENTION_LENGTH` | 200 символов |
| dirty threshold | 3 релевантных сообщения |
| offscreen interval по умолчанию | 6 ходов |
| UI interval | от 4 до 20 ходов |
| минимальный cooldown между significant offscreen событиями | 2 тика |
| минимум significant событий между remote-контактами | 3 |

Пустая память создаётся функцией `emptyParticipantMemory`. Отсутствующая запись
при чтении трактуется как пустая, поэтому старое сохранение без
`participantMemory` не падает.

## 4.3. `Intention`

```ts
interface Intention {
  text: string;
  scope: "location" | "time" | "scene" | "persistent";
  createdAtMessageId: string;
  origin?: "offscreen" | "scene";
}
```

У персонажа одновременно хранится одно активное намерение. Новое замещает старое;
это предотвращает накопление забытых планов.

## 4.4. `Message`

Ключевые новые поля:

| Поле | Значение |
|---|---|
| `characterId` | Кто реально является автором assistant-реплики. |
| `characterName` | Снимок имени на момент создания, переживает удаление/переименование карточки. |
| `addressedTo` | Историческое имя адресата из UI. |
| `targetCharacterId` | Канонический ID адресата для dirty flag и remote thread. При импорте может быть восстановлен из `addressedTo`. |
| `presentCharacterIds` | Snapshot физически присутствующих при создании сообщения. |
| `remoteKind` | Канал remote: `sms`, `call_missed`, `social_post`, `message`. Также помечает пользовательскую часть изолированного remote thread, чтобы она не просачивалась в обычный group context. |
| `isRemoteReply` | Assistant-ответ на уже открытый remote thread. Он остаётся дистанционным, но не считается новым непрочитанным контактом. |
| `isLiveSceneEcho` | Косметическое echo; исключается из stateful-вычислений. |
| `statsSnapshot` | Stats автора после ответа. |
| `statsDelta` | Разница after − before по шкалам автора. |
| `swipes/currentSwipeIndex` | Старый механизм альтернативных реплик; новая память всегда работает по актуальному выбранному тексту. |

Принцип: **сообщение — это не просто текст, а текст плюс автор, момент
присутствия, канал и вычислительная роль**.

## 4.5. `SceneSessionPatch`

Патч может содержать:

- `presencePatch`;
- `compositionPatch`;
- `relationsReplace` или `relationsPatch`;
- `statsPatch` для лидера и участников;
- `summaryPatch`;
- `settingsPatch` для LiveScene/offscreen/interval;
- `participantMemoryPatch`;
- `sceneShiftPatch`;
- `remoteMessagePatch`;
- `baseNotesSignature` и `baseIntentionSignature`;
- `offscreenSubjectId` и `offscreenWasAbsent`;
- `sourceKind` (`user_turn`, `regenerate`, `offscreen_tick`, `memory_extraction`);
- `sourceSnapshotAt`.

Патч — декларативное описание одного логического шага. Сессия не должна
частично обновлять memory, stats и presence разными независимыми write-paths.

# 5. Создание групповой ветки

## 5.1. Сборка из существующих карточек

Точка входа — `GroupSceneModal`.

1. Пользователь выбирает от 2 до 4 карточек.
2. Первый выбранный персонаж становится лидером.
3. Остальные сохраняются в `characterIds` в выбранном порядке.
4. Кнопка выбора поддерживает поиск по имени, описанию, tagline и жанру.
5. Если модалка открыта из карточки героя, `lockedId` фиксирует лидера.
6. `createGroupSession` создаёт один `ChatSession`, копирует initial stats и
   инициализирует memory всех участников.

## 5.2. Начальная история без общего opening

Если `opening` не передан, каждый участник получает собственное стартовое
сообщение:

```text
leader.firstMessage
participant-1.firstMessage
participant-2.firstMessage
...
```

Каждое сообщение получает:

- `characterId`;
- `characterName`;
- `presentCharacterIds` полного начального состава;
- собственный `statsSnapshot`.

Timestamp увеличивается на единицу, чтобы сортировка была стабильной.

## 5.3. AI-генератор группы

Классический group generator живёт в `src/services/characterGenerator.ts` и не
заменяет одиночный V1 generator.

Алгоритм:

1. `clampGroupSize` зажимает размер к 2–4.
2. Формируется один JSON-запрос с общим opening и массивом `characters`.
3. Ожидаются различающиеся голоса, темпераменты и отношения внутри группы.
4. При невалидном ответе выполняется строгая повторная попытка: «только JSON».
5. Если модель снова не смогла отдать группу, герои генерируются по одному;
   каждый следующий получает краткий roster уже придуманных соседей.
6. После этого отдельный запрос генерирует общий opening.
7. Если героев меньше минимального размера, создание отменяется.
8. Карточки сохраняются в библиотеку и сразу собираются в групповую ветку.

### Схема запроса group generator-а

```text
Ты — ведущий нарративный дизайнер и специалист по живому диалоговому AI RolePlay.
Твоя задача — собрать СЦЕНУ из N персонажей для ролевой игры на русском языке:
у каждого свой характер и голос, но всех связывает одна завязка.

ВХОДНЫЕ ПАРАМЕТРЫ:
- пол или свободный выбор пола;
- выбранные теги, стиль речи и сеттинг;
- авторская задумка пользователя, если она есть.

ПРАВИЛА ГРУППЫ:
1. Персонажи должны звучать разно.
2. Между ними есть живые связи: дружба, соперничество, тайная симпатия,
   долг или старая обида.
3. Никакой воды и высокопарных клише.
4. Opening должен собрать всех героев в одной сцене и дать игроку повод вмешаться.

ДЛЯ КАЖДОГО ГЕРОЯ:
- name;
- tagline;
- description;
- personality;
- scenario;
- systemPrompt;
- firstMessage;
- initialStats;
- lorebook.

ОТВЕТ СТРОГО JSON:
{
  "opening": "...",
  "characters": [
    {
      "name": "...",
      "tagline": "...",
      "description": "...",
      "personality": "...",
      "scenario": "...",
      "systemPrompt": "...",
      "firstMessage": "...",
      "initialStats": {
        "trust": 30,
        "affection": 20,
        "closeness": 15,
        "tension": 25,
        "conflict": 0,
        "statusTitle": "Первая встреча"
      },
      "lorebook": [
        { "keys": ["..."], "content": "...", "isActive": true }
      ]
    }
  ]
}
```

Парсер терпим к `characters`, `heroes`, `cast`, `group`, массиву, словарю или
одиночному объекту. Он извлекает JSON из markdown и может чинить оборванный
ответ. После нормализации все карточки получают безопасные defaults.

## 5.4. Открытие с общим opening

Если AI generator передал `opening`, создаётся одно первое сообщение от лица
лидера. Это не означает, что остальные перестали быть в сцене: snapshot
`presentCharacterIds` содержит весь состав, а их индивидуальные stats/memory
уже созданы.

# 6. Жизненный цикл обычного хода

Ниже — фактическая последовательность для `handleSend` и
`callModelAndAppend`.

## 6.1. Шаг 1 — сообщение игрока

`InputBar` создаёт `Message`:

- `sender: "user"`;
- `swipes: [text]`;
- `targetCharacterId` и `addressedTo`, если выбран адресат;
- snapshot `presentCharacterIds`;
- `remoteKind: "message"`, если адресат был отсутствующим remote-контактом.

Пользовательская реплика сначала пишется в `db.messages`. Это позволяет не
терять ввод, даже если последующий API-запрос не удался.

## 6.2. Шаг 2 — определение speaker-а

- одиночный чат: лидер;
- групповой чат с явным присутствующим адресатом: выбранный герой;
- групповой чат без адресата: `chooseSpeaker`;
- `Продолжить`: следующий присутствующий по составу или явный initiative speaker;
- retry после прерванного group-turn: только те участники, которые ещё не
  ответили на последнюю пользовательскую реплику;
- remote target: не обычный group-turn, а isolated remote reply.

## 6.3. Шаг 3 — построение контекста

Для каждого speaker-а берётся stepped/context window. Удаляются system messages.
В group context:

- ordinary assistant messages остаются;
- сообщения других персонажей получают префикс имени;
- собственные прошлые сообщения текущего героя остаются без искусственной
  подписи;
- LiveScene echo исключается из stateful-фильтров;
- remote thread исключается из обычного scene context.

## 6.4. Шаг 4 — system prompt и API-вызов

`buildSystemPrompt` получает:

```ts
{
  speaker,
  session,
  userProfile,
  recentMessages,
  isLocal,
  {
    others,
    currentStats: speakerStats,
    absent,
    relations,
    personalMemory: {
      privateNotes,
      intention
    }
  }
}
```

Далее `requestRoleplayReply` вызывает провайдера через `callLLM`, поддерживая
облачные OpenAI-compatible/Gemini и локальные Ollama/совместимые endpoints.
Стриминг показывает текст в UI, но частичный ответ не сохраняется, если
пользователь нажал Stop.

## 6.5. Шаг 5 — meta-parser

Parser возвращает:

```ts
{
  text,
  innerThought,
  feelingHint,
  stats,
  returnedNames,
  left,
  relations,
  sceneShift,
  intention,
  resolvedIntention,
  metaWarning
}
```

## 6.6. Шаг 6 — декларативный patch

В один `turnPatch` собираются:

- returned/left и новый список presence;
- relations;
- intention/resolved intention speaker-а;
- sceneShift;
- stats speaker-а.

Обычная реплика получает новый `message.id`. Если в ней возникло новое
намерение, `createdAtMessageId` теперь равен этому стабильному ID.

## 6.7. Шаг 7 — LiveScene split

Если включён `liveScene`, parser проверяет хвост ответа на строки вида:

```text
— **Рин:** Ну да.
— **Кай:** *хмыкает*
```

Распознанные строки выносятся в отдельные сообщения с
`isLiveSceneEcho: true`. Основной текст остаётся за выбранным speaker-ом.

## 6.8. Шаг 8 — атомарный commit

`commitPatch` внутри одной Dexie-транзакции:

1. читает свежую сессию;
2. читает актуальные messages;
3. применяет reducer;
4. обновляет session;
5. добавляет assistant message, echo и возможный remote message;
6. обновляет существующее сообщение при regenerate.

## 6.9. Шаг 9 — фоновый upkeep

После ответа игрока `runSceneUpkeep` запускается асинхронно и не задерживает
видимую основную реплику.

# 7. Выбор говорящего: адресат, роутер, fallback и «Продолжить»

## 7.1. Явный адресат

В `InputBar` появляется строка `Ответит` с аватарами присутствующих героев.
Выбор адресата:

- не записывает техническую подсказку в историю;
- передаётся в prompt как отдельная служебная user-инструкция;
- не меняет composition;
- для присутствующего направляет обычный ход;
- для absent remote-контакта направляет isolated reply.

## 7.2. Автоматический router

`groupRouter.ts` делает отдельный лёгкий запрос. Он не генерирует художественную
реплику, а выбирает только имя первого speaker-а.

Приоритеты, зашитые в prompt:

1. игрок назвал персонажа по имени;
2. у кого-то есть активное подходящее намерение;
3. текущая реплика сильнее задела кого-то по характеру/relations;
4. не повторять того, кто только что говорил, если есть кандидат;
5. при обращении ко всем — самый активный/заинтересованный или герой с планом.

Если запрос router-а упал или дал неизвестное имя:

```text
mentionedCharacter
    ?? firstPresentThatIsNotLastSpeaker
    ?? firstPresent
```

Private notes не передаются router-у. Передаются только краткие intention-тексты
присутствующих — намерение является планом действия, но не приватной мыслью.

## 7.3. Точный prompt router-а

```text
Ты — режиссёр ролевой сцены с несколькими персонажами.
Определи, кто из них отвечает СЕЙЧАС первым.

ПЕРСОНАЖИ В СЦЕНЕ:
- Имя (id: ...): краткий personality/tagline

ТЕКУЩИЕ НАМЕРЕНИЯ ПЕРСОНАЖЕЙ:
- Имя: краткий план

ОТНОШЕНИЯ ВНУТРИ ГРУППЫ:
- Имя → Имя/группа: текст связи

АТМОСФЕРА СЦЕНЫ: ...

ПОСЛЕДНЯЯ РЕПЛИКА ИГРОКА (Имя игрока): «...»

КАК ВЫБИРАТЬ:
1. Если игрок обратился к кому-то по имени — отвечает он.
2. Если активное намерение создаёт подходящий повод — это сильный кандидат.
3. Иначе отвечает тот, кого реплика задела сильнее.
4. Не отдавай ход тому, кто только что говорил, если есть другие.
5. При обращении ко всем выбери самого активного/заинтересованного.

Ответь строго одной строкой:
[Отвечает: Имя]
```

Parser принимает `[Отвечает: ...]`, `Отвечает: ...`, `<speaker>...</speaker>`
и свободное упоминание имени.

## 7.4. `Продолжить`

В одиночном чате это продолжение текущей сцены тем же лидером; управляющая
инструкция не имитирует молчание игрока. В группе — следующий присутствующий
после последнего полноценного speaker-а с той же инструкцией продолжить сцену.
LiveScene echo и remote
ответы не сдвигают эту очередь.

## 7.5. Retry после оборванного group-turn

`pendingSpeakers` ищет последнюю user-реплику и собирает assistant-ответы после
неё. Из answered исключаются:

- `isLiveSceneEcho`;
- remote messages;
- ответы, которые не являются полноценными сценическими ходами.

В результате retry вызывает модель только для ещё не ответивших героев.

# 8. Как строится контекст запроса и кто что видит

## 8.1. Подписи assistant-реплик

`buildAssistantLabeler` сравнивает `message.characterId` с текущим speaker-ом.

Пример для запроса Рин:

```text
Странник: — Вы обе чего молчите?
— Ая пожимает плечами.
Ян: — Я просто слушаю.
```

Свои прошлые реплики Рин получает без префикса `Рин:`; чужие получают имя.
Это позволяет одной истории оставаться последовательностью assistant-turns для
API и при этом не смешивать голоса.

## 8.2. Visibility snapshot

Каждое новое group message получает snapshot `presentCharacterIds`.
`messageVisibleToCharacter` использует его так:

- system и LiveScene echo не являются источником личного знания;
- user-message виден адресату, а без адресата — присутствующим по snapshot;
- собственная assistant-реплика видна собственному герою;
- assistant-реплика другого героя видна только если герой присутствовал в момент
  создания сообщения;
- старые сообщения без snapshot обрабатываются консервативно.

Это не полноценный knowledge graph, но это надёжная MVP-граница между «было в
истории» и «персонаж реально мог слышать».

## 8.3. Релевантность для dirty flag

Для персонажа учитываются:

- его собственные полноценные assistant-реплики;
- пользовательские сообщения, адресованные ему;
- чужие assistant-реплики, где он упомянут по имени и был видим.

Не учитываются как самостоятельный новый опыт:

- LiveScene echo;
- system messages;
- технические router-инструкции.

Remote-thread остаётся частью личного опыта своего адресата, но исключается из
общего scene context и общей нейтральной хроники.

## 8.4. Слои видимости

```text
                       Director
                       /      \
              full memory     full scene controls
                    │
        ┌───────────┴───────────┐
        │                       │
  current speaker         active scene/router
  own private notes       no private notes
  own intention           only visible roster/relations
        │                       │
        └───────────┬───────────┘
                    │
              absent character
          own offscreen state only
          + remote isolated thread
```

# 9. Система промптов: полный разбор слоёв

`buildSystemPrompt` не хранит один статичный prompt-файл. Он собирает prompt из
условных блоков в зависимости от модели, состава, presence, stats, памяти,
настроек ветки и режима скрытых мыслей.

## 9.1. Порядок основного roleplay system prompt

Фактические слои:

1. Meta protocol — локальные теги или облачный JSON.
2. Форматирование: тире для речи, звёздочки для действий, запрет говорить за игрока.
3. Имя и роль текущего персонажа.
4. Внешность/описание.
5. Personality и манера речи.
6. Scenario и предыстория.
7. `character.systemPrompt`.
8. Профиль игрока.
9. Групповая сцена и roster присутствующих.
10. Presence block для absent.
11. Relations.
12. Личная память текущего speaker-а.
13. Psychological realism / slow burn.
14. Natural speech, если включён.
15. Dynamic events или suspense.
16. Summary: в группе нейтральная хроника, в одиночном чате legacy synopsis.
17. Legacy extracted facts, если они есть.
18. Lorebook.
19. Stats конкретного speaker-а.
20. Director notes.
21. Thought mode.

Важно: `privateNotes` не добавляются в этот prompt для другого персонажа.

## 9.2. Общий групповой блок

Для текущего героя формируется примерно такой текст:

```text
### ГРУППОВАЯ СЦЕНА: НЕСКОЛЬКО ПЕРСОНАЖЕЙ
Сейчас в сцене несколько персонажей. Ты отыгрываешь ТОЛЬКО [speaker].
Кто ещё здесь:
- [name]: [короткий personality/description]

Правила групповой сцены:
1. Реагируй на других как на живых людей, но никогда не пиши за них
   реплики, мысли или действия.
2. Не отвечай за игрока: его ход приходит отдельно.
3. Не подписывай собственную реплику именем и не добавляй заголовок.
4. Не пересказывай чужие реплики и не подводи общий итог.
5. ПОЛИФОНИЯ СЦЕНЫ И ПРИСУТСТВИЕ ИГРОКА: игрок находится в сцене, поэтому учитывай его присутствие и никогда не говори и не действуй за него. Но он не обязан быть адресатом каждой реплики, судьёй или посредником каждого конфликта. Позволяй персонажам самостоятельно вести разговор между собой: спорить, перебивать, договариваться, менять тему, молчать и развивать собственные отношения. Обращайся к игроку, когда он непосредственно вовлечён, его реакция естественно важна или сцене пора передать ему ход; не заканчивай каждый ответ вопросом к игроку и не возвращай разговор к нему искусственно.
```

Если LiveScene активен, добавляется:

```text
6. ЖИВАЯ СЦЕНА: если реплика задела кого-то ещё, в конце можно добавить
   1–2 короткие реакции присутствующих, каждую с новой строки:
   — **Имя:** реплика
   Это единственное короткое исключение из запрета писать за других.
```

## 9.3. Блок сценического присутствия

Если есть absent:

```text
### СЦЕНИЧЕСКОЕ ПРИСУТСТВИЕ
В сцене сейчас: [присутствующие].
За кадром:
- [Имя] — [причина]

Не говори за отсутствующих и не действуй от их имени.
Если герой возвращается только по правдоподобному поводу — опиши появление и добавь `returned` в cloud JSON или `<returned names="Имя" />` в local protocol.
Если присутствующий сам уходит — опиши уход и добавь `left` в cloud JSON или `<left names="Имя" reason="..." />` в local protocol.
Не уводи всех сразу и не возвращай только что ушедшего без причины.
```

## 9.4. Блок relations

```text
### ВЗАИМООТНОШЕНИЯ ВНУТРИ ГРУППЫ
- [from] → [to/вся группа]: [текст]

Показывай отношения через подтекст, интонации, взгляды и мелкие детали,
а не пересказывай их справочно. Если отношение действительно изменилось,
добавь relations только для изменившейся пары.
```

## 9.5. Блок личной памяти

Он добавляется только текущему speaker-у:

```text
### ТВОЯ ЛИЧНАЯ ПАМЯТЬ (ВНУТРЕННИЙ СЛОЙ)
Что ты помнишь, знаешь, подозреваешь и держишь при себе:
- [private note 1]
- [private note 2]

ТВОЁ ТЕКУЩЕЕ НАМЕРЕНИЕ: «[intention]».
Держи план в голове и мягко двигай сцену к нему при естественном поводе,
но не объявляй его напрямую и не форсируй события.
Если он выполнен — resolvedIntention.
Если возник новый устойчивый план — intention.
```

Приватная заметка может быть субъективной и неполной. Она не становится
объективной общей правдой только потому, что попала в prompt.

## 9.6. Общая нейтральная хроника в roleplay prompt

В group prompt `session.summary` маркируется так:

```text
### СЮЖЕТНЫЙ КОНТЕКСТ (НЕЙТРАЛЬНАЯ ХРОНИКА СЦЕНЫ)
Объективная хроника событий от третьего лица — общая для всех участников:
[summary]

Личные выводы и подозрения должны находиться в ТВОЕЙ ЛИЧНОЙ ПАМЯТИ,
а не в этой общей хронике.
```

## 9.7. Общие behavioural-модули

Групповой prompt сохраняет прежние V1-модули:

- slow burn и инерция собственной жизни;
- барьеры по trust;
- Anti-Rush и штраф за навязчивое нарушение границ;
- поступки важнее слов;
- natural spoken dialogue;
- dynamic events или suspense;
- thought mode: censor, counterpoint, stream, tactical, instinct.

Новая память не отменяет эти модули и не превращает каждый контакт в романтику,
травму или драму.

# 10. Мета-протокол V1: облачные JSON и локальные теги

Новая симметричная память не меняет базовую V1-схему генерации. Она расширяет
meta-протокол дополнительными полями.

## 10.1. Облачный режим

`META_PROTOCOL_INSTRUCTION` просит модель завершать ответ блоком:

```text
```meta
{
  "innerThought": "...",
  "feelingHint": "...",
  "stats": {
    "trust": 50,
    "affection": 30,
    "closeness": 20,
    "tension": 10,
    "conflict": 0,
    "statusTitle": "..."
  },
  "returned": ["Имя"],
  "left": {"Имя": "короткая причина"},
  "relations": [
    {"from": "Имя", "to": "Имя", "text": "..."}
  ],
  "sceneShift": {
    "time": "hours" | "day" | "days" | null,
    "locationChanged": true | false
  },
  "intention": {
    "text": "короткий план",
    "scope": "location" | "time" | "scene" | "persistent"
  },
  "resolvedIntention": true
}
```
```

Необязательные поля должны появляться только при наличии события. В частности,
`sceneShift` не должен добавляться при обычном продолжении диалога.

## 10.2. Локальный режим

Для local endpoint prompt требует в начале:

```text
<thought>1–2 предложения скрытых мыслей от первого лица</thought>
<stats trust="+1" affection="0" tension="-1"
       hint="Краткое чувство" status="Актуальный статус"/>
[необязательные служебные теги сразу после stats]
[затем художественный roleplay-текст]
```

Group-specific расширения:

```text
<returned names="Имя" />
<left names="Имя" reason="короткая причина" />
<relation from="Имя" to="Имя" text="как теперь относится" />
<sceneShift time="hours" location="true" />
<intention scope="location">короткий устойчивый план</intention>
<resolvedIntention />
```

В `scope` указывается ровно одно значение: `location`, `time`, `scene` или
`persistent`; вертикальные черты не выводятся. Технические теги идут сразу
после stats и не должны оставаться в художественном тексте или появляться после
него.

## 10.3. Поведение parser-а

`parseMetaBlock`:

1. ищет последний валидный fenced meta/json block;
2. удаляет дублирующие meta-блоки;
3. умеет найти trailing JSON без ограждения;
4. чинит BOM, «умные» кавычки и висячие запятые;
5. читает локальные теги;
6. облачные JSON-значения перекрывают одноимённые локальные значения;
7. при битом meta-блоке удаляет технический мусор и возвращает `metaWarning`,
   но не выдумывает stats;
8. сохраняет обычные code blocks, которые не являются meta.

## 10.4. Stats normalization

Parser принимает абсолютные числа и строковые дельты:

```text
"trust": 70   → абсолютное значение 70
"trust": "+7" → current + 7
"trust": "-4" → current - 4
```

Все значения clamp-ятся к 0–100. Если шкала не указана, сохраняется предыдущее
значение. `attraction` поддерживается только если она уже существует у V2 stats;
у V1 она не появляется сама.

# 11. Динамическое присутствие: уходы, возвращения и причины

## 11.1. Ручное управление

### ScenePresenceBar

В шапке группового чата отображаются pill-элементы:

- зелёная точка — `present`;
- серая точка — `absent`;
- голубая точка — есть новый remote-контакт.

При попытке убрать героя из сцены через верхний бар открывается prompt причины:

```text
ушёл в гараж
спит
вышел покурить
уехал по делам
```

Причина сохраняется в `absentReasons` и попадает в roleplay/offscreen prompt.
Последнего присутствующего нельзя убрать так, чтобы сцена осталась пустой.

### DirectorPanel

В панели те же переключатели доступны у каждого участника. Там можно также:

- менять состав;
- менять порядок;
- давать ход конкретному присутствующему;
- удалить участника из ветки;
- ввести отсутствующего обратно.

## 11.2. Уход из model response

Модель может вернуть:

```json
{"left":{"Рин":"ушла за курткой"}}
```

или локальный тег:

```text
<left names="Рин" reason="ушла за курткой" />
```

Parser нормализует данные. `matchLeftCharacters` принимает только имена
участников, которые действительно сейчас присутствуют. Затем обычный ход
создаёт `presencePatch` с новым `activeCharacterIds`.

## 11.3. Возвращение

Модель может вернуть:

```json
{"returned":["Рина"]}
```

Сопоставление терпимо к падежам и лёгким формам имени. Возвращаются только те,
кто реально был в `absent`. Если модель назвала неизвестного персонажа, ничего не
происходит.

## 11.4. Почему это не метагейминг

В prompt прямо запрещено говорить за absent. Возвращение требует художественного
следа: шаги, голос, открывшаяся дверь, сообщение о возвращении. Само изменение
presence хранится в meta-state, а не проговаривается моделью как техническая
инструкция.

# 12. Симметричная личная память всех участников

## 12.1. Что хранится

Для каждого героя:

- до пяти субъективных private notes;
- одно intention;
- pointer последней memory extraction;
- pointer начала отсутствия;
- счётчики offscreen cooldown;
- pointer последнего offscreen tick.

Лидер не получает специального исключения: в `createGroupSession` запись
создаётся одновременно для `[leader, ...participants]`.

## 12.2. Как формируется personal transcript

`buildPersonalTranscriptSince` берёт сообщения после pointer и оставляет только
то, что персонаж мог видеть:

- свою реплику;
- пользовательскую реплику, адресованную ему;
- присутствующие в момент сообщения чужие реплики;
- собственные remote-реплики и remote-ответы для личной истории адресата.

LiveScene echo полностью исключается как самостоятельный источник внутреннего
состояния: это текст, сформулированный моделью основного speaker-а.

## 12.3. Prompt персональной экстракции

Текущий prompt практически дословно задаёт следующие границы:

```text
Ты анализируешь недавние события ролевой сцены с точки зрения ОДНОГО
конкретного персонажа — [Имя]. Ты не рассказчик всей сцены, ты психолог,
который восстанавливает внутренний мир именно этого человека.

ПОСЛЕДНИЕ СОБЫТИЯ СЦЕНЫ:
[personal fragment]

ТЕКУЩИЕ ЛИЧНЫЕ ЗАМЕТКИ [Имя]:
- ...

ТЕКУЩЕЕ НАМЕРЕНИЕ [Имя]:
[текст или «нет активного намерения»]

ЗАДАЧА:
1. Определи, узнал ли персонаж что-то новое и значимое лично для себя.
2. Учитывай только то, что он реально мог видеть или слышать.
3. Если информация пришла от другого героя, пометь источник:
   "[От Имени]: содержание услышанного".
4. Удали опровергнутое, объедини дубли, добавь новые важные пункты.
5. Оставь не более 5 заметок, важное поставь выше.
6. Выполненное/отменённое intention очисти.
7. Если ничего важного не произошло — верни состояние без изменений.

Ответ строго JSON:
{
  "privateNotes": ["..."],
  "intention": {
    "text": "...",
    "scope": "location" | "time" | "scene" | "persistent"
  } | null
}
```

Обязательная формулировка «не выдумывай внутреннюю жизнь ради активности»
снижает риск появления одинаковых искусственных драматических записей.

## 12.4. Parser и санитизация

`parsePersonalExtraction`:

- принимает только JSON-объект с массивом `privateNotes`;
- очищает пробелы, дубли и пустые строки;
- обрезает заметку до 300 символов;
- обрезает список до пяти;
- нормализует intention и его scope;
- при полном провале возвращает `null`, а вызывающий код сохраняет старое
  состояние вместо выдуманного.

## 12.5. Накопительный характер

Каждая extraction получает текущий список заметок и обязана вернуть уже
консолидированную версию. Отдельный глобальный таймер для всех участников не
используется: у каждого персонажа свой pointer и свой dirty count.

# 13. Грязный флаг персональной памяти

## 13.1. Почему не таймер

Глобальное «каждые N секунд» или «каждые N сообщений для лидера» плохо подходит
группе: молчащий персонаж начинает получать бесполезные запросы, а активный
может не успеть сохранить важную мысль. Поэтому extraction due вычисляется по
релевантным сообщениям конкретного героя.

## 13.2. Алгоритм `isExtractionDue`

```text
memory = getParticipantMemory(session, characterId)

если lastExtractedMessageId == null:
    pointer = null и считаем историю с начала
иначе:
    pointer = resolveMemoryPointer(
        messages,
        lastExtractedMessageId,
        fallback = последняя собственная реплика
    )

count = countRelevantMessagesSince(messages, characterId, pointer, cast)
due = count >= PERSONAL_MEMORY_DIRTY_THRESHOLD
```

Порог по умолчанию — 3 релевантных сообщения.

## 13.3. Как выполняется extraction в upkeep

Для каждого `freshPresent` участника последовательно:

1. читается его memory;
2. проверяется dirty flag;
3. строится personal transcript;
4. вызывается personal extractor;
5. результат записывается `SceneSessionPatch` с base signatures;
6. `lastExtractedMessageId` устанавливается на актуальный последний message ID.

Offscreen-персонаж не получает обычную extraction только потому, что в основной
сцене накопились сообщения: его внутренний слой развивается через собственный
offscreen tick.

## 13.4. Защита от устаревшего extraction

Патч несёт:

```ts
baseNotesSignature: notesSignature(notesAtPromptTime)
baseIntentionSignature: intentionSignature(intentionAtPromptTime)
```

Если DirectorPanel или другой фоновой процесс успел изменить notes/intention,
reducer не перезаписывает свежие значения старым ответом модели. Проверка
отдельная для notes и intention.

# 14. Нейтральная общая хроника

## 14.1. Отличие от старого synopsis

Старый V1 synopsis мог быть субъективной памятью основного персонажа. В новом
групповом контуре `session.summary` должен быть общей хроникой:

- от третьего лица;
- только наблюдаемые события;
- без приватных подозрений;
- без внутренней правды отдельного героя;
- компактно и накопительно.

## 14.2. Prompt хроникёра

```text
Ты — беспристрастный хроникёр ролевой сцены. Зафиксируй объективные события
последнего фрагмента со стороны, как их видел бы нейтральный наблюдатель.

ПОСЛЕДНИЕ СОБЫТИЯ:
[fragment]

ТЕКУЩАЯ ОБЩАЯ ХРОНИКА:
[currentSummary или «пока пусто»]

ПРАВИЛА:
1. Пиши от третьего лица.
2. Фиксируй только речь, физические действия, приход/уход и объективные факты.
3. Не включай внутренние переживания, подозрения и недосказанные мысли.
4. Не пересказывай всё заново: компактно дополни или скорректируй хронику.
5. Если ничего существенного не произошло — верни без изменений.

Ответь только обновлённым текстом, без заголовка.
```

## 14.3. Триггер

Автоматическая хроника обновляется, когда накопилось примерно
`MEMORY_EXTRACT_INTERVAL = 8` новых сообщений и история достаточно велика.
Отдельно используются:

- `lastChronicleMsgCountRef`;
- `lastChronicleMessageIdRef`;
- локальная переменная `currentUpkeepSummary`, чтобы последовательные offscreen
  patches не перетирали более свежий public consequence.

Дистанционные сообщения исключены из общей хроники, чтобы приватный remote-thread
не становился знаниями активных персонажей.

## 14.4. Ручное обновление

В DirectorPanel кнопка «Актуализировать» для групповой сцены вызывает именно
`requestNeutralChronicle`. Редактор может также вручную изменить весь summary.

Старый `storyLog` и кнопка legacy-профиля сохраняются для V1-совместимости и
не должны путаться с новым симметричным personal memory layer.

# 15. Внекадровая жизнь и offscreen tick

## 15.1. Что запускает тик

`isOffscreenTickDue` работает по OR:

### Interval trigger

```text
turnsSinceLastTick >= configuredInterval
и
turnsAbsent >= configuredInterval
```

### Scene-shift trigger

Если последний ход сообщил `sceneShift.time`, offscreen tick может быть вызван
раньше полного interval, но не чаще, чем после двух ходов сцены с прошлого тика.

Если `offscreenLifeEnabled === false`, тик не запускается. Если персонаж снова
present, тик не запускается.

## 15.2. Указатели отсутствия

При переходе `present → absent` reducer устанавливает:

- `absentSinceMessageId` на последний актуальный message ID;
- `lastTickAtMessageId` на тот же ID;
- `ticksSinceLastSignificant` в безопасное cooldown-состояние;
- `significantSinceLastContact` в 0.

При возвращении `absent → present` `absentSinceMessageId` очищается.

## 15.3. Prompt offscreen tick

Фактически передаваемые блоки:

```text
Ты моделируешь внутреннюю жизнь персонажа [Имя] ЗА КАДРОМ — пока он физически
отсутствует в основной сцене.

ПРИЧИНА ОТСУТСТВИЯ:
[reason или «неизвестна»]

ПОСЛЕДНЕЕ ИЗВЕСТНОЕ ЕЙ СОСТОЯНИЕ:
Личные заметки: [private notes]
Текущее намерение: [intention или «нет»]

ОБЪЕКТИВНАЯ ХРОНИКА СЦЕНЫ ЗА ВРЕМЯ ОТСУТСТВИЯ:
[neutral chronicle]

ЕЁ ОТНОШЕНИЯ:
[relations digest + trust/affection/status]

ПРИМЕРНО ПРОШЛО ВРЕМЕНИ: [немного / несколько часов / около суток / дни]

ЗАДАЧА:
Определи, произошло ли с персонажем нечто, что стоит зафиксировать.
Она продолжает жить собственной жизнью, но событие не обязательно.

СТРОГИЕ ПРАВИЛА:
1. Дефолтный ответ — ничего принципиально нового не произошло.
2. Персонаж не знает того, чему не был свидетелем и о чём ему не сообщили.
3. Большинство опыта может остаться только внутренним.
4. Не форсируй резкие, разрушительные и необратимые решения.
5. Объективный след заполняет worldConsequence.
6. Дистанционный контакт заполняет contactAction только при характерном поводе.

Ответ строго JSON:
{
  "significant": boolean,
  "updatedPrivateNotes": ["..."] | null,
  "intention": {"text":"...","scope":"..."} | null,
  "worldConsequence": {
    "text":"...",
    "reveal":"public" | "private_until_surfaced"
  } | null,
  "contactAction": {
    "kind":"sms" | "call_missed" | "social_post" | "message",
    "text":"..."
  } | null
}

Если significant=false, остальные поля должны быть null.
```

## 15.4. Parser результата

`parseOffscreenTickResult` жёстко нормализует:

- `significant` — только literal `true`;
- при `false` все остальные поля принудительно обнуляются;
- notes — общие лимиты 5 × 300;
- intention — белый список scopes, неизвестный scope становится `scene`;
- world consequence — максимум 300 символов и только два вида reveal;
- contact — только четыре допустимых remote kind и максимум 500 символов.

## 15.5. Hard cooldowns в коде

Prompt — не единственная защита. `buildOffscreenPatch` повторно проверяет:

```text
если significant=true, но ticksSinceLastSignificant < 2:
    принудительно преобразовать результат в significant=false
```

Для contactAction нужны одновременно:

```text
turnsAbsent >= interval
и
memory.significantSinceLastContact + 1 >= 3
```

Если gate не пройден, контакт не создаётся, даже если модель его предложила.

## 15.6. Последствия значимого события

### `public`

Текст добавляется в общую нейтральную хронику и может стать частью будущего
контекста активных героев.

### `private_until_surfaced`

Текст добавляется в private notes героя. Активные персонажи не видят его, пока
он сам не расскажет или не появится иной допустимый наблюдаемый след.

### `contactAction`

Создаётся отдельное assistant-сообщение с `remoteKind`. Оно не меняет
`activeCharacterIds` и не отправляет героя обратно в обычный кадр.

## 15.7. Presence Guard для race condition

Пока offscreen-модель думает, герой может вернуться. При применении патча reducer
сравнивает:

```text
offscreenWasAbsent — каким герой был при запуске
isAbsentNow        — каким он стал при записи
```

Если статус изменился:

- внутренний пережитый опыт/notes ещё может примениться по base signature;
- служебное намерение, tick counters и remote contact из устаревшего кадра не
  возвращают героя за сцену и не откатывают его новое состояние.

# 16. Дистанционные контакты: SMS, звонки, посты и сообщения

## 16.1. Каналы

```ts
type RemoteKind = "sms" | "call_missed" | "social_post" | "message";
```

Контакт появляется как message с:

- `characterId` отсутствующего героя;
- `characterName` snapshot;
- `presentCharacterIds: []`;
- `remoteKind`;
- собственным message ID.

## 16.2. Визуальное отображение

`MessageBubble` показывает голубой badge:

- SMS;
- Пропущенный звонок;
- Публикация;
- Сообщение из-за кадра.

`ScenePresenceBar` и `InputBar` показывают голубой индикатор нового контакта.
Он не меняет зелёный/серый статус физического присутствия.

## 16.3. Изолированный ответ

Когда игрок выбирает remote-контакт:

1. user message получает `targetCharacterId` и remote marker;
2. собирается только thread из сообщений этого героя и адресованных ему user turns;
3. создаётся `remoteSession`, где очищаются:
   - `isGroup`;
   - `characterIds`;
   - `activeCharacterIds`;
   - `absentReasons`;
   - `relations`;
   - `summary`;
   - `storyLog`;
   - `extractedFacts`;
   - `directorNotes`;
4. сохраняется собственный профиль/статы/личная память target-а;
5. в system prompt добавляется прямое правило: герой физически вне основной сцены,
   отвечает как в переписке и не знает текущие события кадра;
6. reply получает `isRemoteReply`, канал и `presentCharacterIds: []`;
7. stats/intention и сообщение записываются одним patch commit.

## 16.4. Что remote не делает

Remote-контакт:

- не добавляет героя в `activeCharacterIds`;
- не делает его кандидатом обычного router-а;
- не считается обычным сценическим ходом;
- не попадает в общую нейтральную хронику, suggestions, rotation или legacy group facts;
- не раскрывается активным героям через обычный prompt и не меняет их общий контекст;
- не отменяет его absent reason.

При этом адресованный герой может сохранить собственный remote-опыт в личном
слое и получить обновление своих stats/intention: это не group memory и не
последняя сценическая delta активных участников.

# 17. Intention: намерения и скоупы

## 17.1. Что считается намерением

Intention — это устойчивый план, который живёт дольше текущей реплики:

```text
«после разговора проверить дверь»
«не дать Рин остаться с Каем наедине»
«найти источник шума»
```

Это не:

- разовая эмоция;
- текущая реакция;
- private note;
- техническое распоряжение игрока.

## 17.2. Скоупы

| Scope | Intention переживает | Intention очищается при |
|---|---|---|
| `location` | обычные реплики и скачок времени в той же локации | смене места (`locationChanged`) |
| `time` | смену места без скачка времени | `sceneShift.time != null` |
| `scene` | обычное продолжение | смене места или времени |
| `persistent` | смену места и времени | только выполнением/отменой/ручным завершением |

`intentionSurvivesShift` применяется reducer-ом ко всем memory entries.

## 17.3. Источники intention

### Из основного roleplay response

- cloud JSON `intention`/`resolvedIntention`;
- local `<intention>`/`<resolvedIntention/>`;
- `createdAtMessageId` = ID текущей assistant-реплики;
- `origin: "scene"`.

### Из offscreen tick

- intention возвращается вместе с offscreen result;
- `origin: "offscreen"`;
- происхождение привязывается к последнему message ID фоновой проверки.

### Из DirectorPanel

Пользователь может вручную изменить текст, scope или завершить план.

## 17.4. Router visibility

Router видит краткое намерение присутствующего, чтобы не терять естественные
реакции и позволять плану привести героя к действию. Router не видит private
notes, потому что план и внутренняя субъективная память — не одно и то же.

# 18. Связи внутри группы и индивидуальные шкалы

## 18.1. `SceneRelation`

```ts
interface SceneRelation {
  id: string;
  from: string;
  to?: string;
  text: string;
  updatedAt?: number;
}
```

`to` без значения означает отношение к группе в целом.

## 18.2. Обновление моделью

Модель должна писать только действительно изменившиеся связи. Parser принимает:

```json
{"relations":[
  {"from":"Рин","to":"Кай","text":"начала ревновать"}
]}
```

или local:

```text
<relation from="Рин" to="Кай" text="начала ревновать" />
```

`mergeSceneRelations`:

1. сопоставляет from/to с известными участниками;
2. игнорирует незнакомые имена;
3. обновляет существующую пару, сохраняя её ID;
4. добавляет новую пару только до лимита 12;
5. ставит `updatedAt` и возвращает список changed для toast;
6. не плодит дубль, если текст не изменился.

## 18.3. Ручное редактирование

DirectorPanel позволяет выбрать:

- кто думает (`from`);
- о ком (`to` или вся группа);
- текст отношения;
- удалить или добавить строку.

## 18.4. Индивидуальные stats

Лидер продолжает жить в `currentStats`. Участники — в
`participantStats[characterId]`.

При ответе:

```text
speakerStats = statsForCharacter(session, speaker.id)
newStats = parsed.stats ?? speakerStats

speaker == leader
    → statsPatch.leader
speaker != leader
    → statsPatch.participants[speaker.id]
```

Каждое полноценное сообщение сохраняет `statsSnapshot` и `statsDelta`. Echo и
remote-контакты не подменяют последнюю сценическую дельту в StatsPanel.

# 19. LiveScene: косметические echo-реакции

## 19.1. Зачем нужен режим

Без LiveScene один model call говорит строго за одного героя. С LiveScene он
может коротко показать, что другие присутствующие физически реагируют в том же
моменте, но архитектурно это всё равно один основной ход.

## 19.2. Parser хвоста

`splitLiveSceneReactions`:

- ищет только подряд идущий хвост ответа;
- принимает максимум 2 реакции;
- требует тире и жирное имя;
- сопоставляет имя только с текущими присутствующими;
- не допускает реакцию основного speaker-а на самого себя;
- если весь ответ оказался «реакцией» без mainText, не разделяет его;
- не распознанные имена возвращаются обратно в основной текст.

## 19.3. Echo message

```ts
{
  sender: "assistant",
  characterId: matchedCharacter.id,
  characterName: matchedCharacter.name,
  isLiveSceneEcho: true,
  presentCharacterIds: currentPresentIds,
  swipes: [reactionText]
}
```

## 19.4. Isolation rules

Echo:

- не меняет `statsPatch`;
- не является отдельным speaker-turn;
- не учитывается `pendingSpeakers`;
- не меняет `lastAssistantSpeakerId`;
- не создаёт dirty memory для приписанного персонажа;
- не обновляет relations от имени персонажа echo;
- не определяет последнюю stats delta;
- не считается источником знания в personal transcript.

Это ключевое отличие от настоящего полифонического хода.

# 20. Единый `SceneSessionPatch`, reducer и атомарность

## 20.1. Почему введён reducer

Без одной точки записи возможны гонки:

```text
main reply читает старую session
memory extraction читает ту же старую session
offscreen tick читает ту же старую session
последний update перезаписывает чужие изменения
```

`reduceScenePatch` устраняет это для группового state layer.

## 20.2. Порядок применения внутри reducer-а

`applyPatchToDraft` последовательно применяет:

1. composition;
2. presence и переходы absent/present;
3. `relationsReplace`;
4. `relationsPatch`;
5. stats;
6. summary;
7. sceneShift и invalidation intentions;
8. participantMemory;
9. settings;
10. remote message creation.

Несколько patches можно передать в `reduceScenePatches`: каждый видит результат
предыдущего, а не исходную session.

## 20.3. Presence transitions

Reducer обслуживает:

```text
present → absent
    absentSinceMessageId = current lastMessageId
    tick counters reset

absent → present
    absentSinceMessageId = null
    absentReasons[id] удаляется
```

Composition reducer дополнительно очищает memory/stats/reasons/relations удалённых
из состава участников.

## 20.4. Stale memory patch

Для notes/intention используются base signatures. Если текущая запись не равна
базе patch-а:

- устаревшие notes не применяются;
- устаревшее intention не применяется;
- независимые поля патча могут продолжить применяться.

## 20.5. Dexie transaction

`commitPatch` делает read/reduce/write/add в `db.transaction("rw", ...)`.
Это особенно важно для:

- обычного turn + echo;
- regenerate + обновление существующего message + echo;
- offscreen patch + remote message;
- memory extraction параллельно с ручной правкой.

## 20.6. Presence Guard

Offscreen patch дополнительно проверяется через
`offscreenSubjectId/offscreenWasAbsent`. Устаревший patch не может:

- вернуть героя в обычный кадр;
- подменить текущий remote state;
- восстановить старое intention поверх нового presence.

Его личный опыт может сохраниться, если base signature ещё подходит.

# 21. Rewind safety, импорт, clone и каскады

## 21.1. Только message IDs

Новые указатели — это:

- `lastExtractedMessageId`;
- `absentSinceMessageId`;
- `lastTickAtMessageId`;
- `Intention.createdAtMessageId`.

Числовые позиции сообщений для новой логики не сохраняются.

## 21.2. Перемотка

`rewindToMessage` удаляет сообщения после выбранной точки. При следующем чтении:

- `resolveMemoryPointer` проверяет, существует ли сохранённый ID;
- если ID исчез, используется безопасный fallback или `null`;
- dirty count/offscreen count пересчитываются по фактической актуальной истории;
- отсутствующий pointer не приводит к обращению к несуществующему индексу.

Полная историческая отмена уже применённых stats/relations/summary не является
задачей старого `rewindToMessage`; это именно безопасная работа указателей и
будущих вычислений.

## 21.3. Импорт backup

`importBackup`:

1. санитизирует characters;
2. санитизирует messages и добавляет недостающие IDs;
3. санитизирует sessions;
4. очищает pointers, которые не существуют среди сообщений этой session;
5. пишет всё в одной Dexie transaction.

Новые поля optional, поэтому старый backup без них не ломается.

## 21.4. Clone

`cloneSession` копирует session state и создаёт новые message IDs. Если старый
memory pointer указывает на ID оригинала, runtime resolver не падает и использует
fallback. Это безопаснее числового индекса, хотя origin pointer при clone не
является автоматически картой `oldId → newId`.

## 21.5. Удаление персонажа

Если удаляется лидер:

- удаляется его session и её messages.

Если удаляется дополнительный участник:

- он удаляется из `characterIds`;
- удаляются его participant stats;
- удаляется его participant memory;
- удаляется absent reason;
- удаляются relations, где он `from` или `to`;
- очищается его active presence.

Старые сообщения с его `characterName` сохраняют исторический голос в ленте.

# 23. Совместимость V1, V2, старых сохранений и API

## 23.1. V1 generator и group generator

Классический `generateAiCharacter` остаётся прежним. Group generator — отдельный
контур с собственным JSON opening/characters. Никакой новый memory/offscreen
механизм не заменяет V1 generator.

## 23.2. Character DNA V2

`Character` может иметь:

```ts
blueprintV2?: CharacterBlueprintV2;
generatorVersion?: number;
```

V2 также может добавлять optional `attraction` в `RelationshipStats`.

Group runtime работает с общим интерфейсом `Character`, поэтому V2-персонажа
можно добавить в группу вручную. Отсутствие `blueprintV2` у V1-карточки не
считается ошибкой.

## 23.3. Старые `ChatSession`

При загрузке:

- отсутствующий `characterIds` → одиночная ветка;
- отсутствующий `activeCharacterIds` → все присутствуют;
- отсутствующий `participantMemory` → empty state при чтении;
- отсутствующий `liveScene` → enabled;
- отсутствующий `offscreenLifeEnabled` → enabled;
- отсутствующий interval → resolver default 6;
- отсутствующий `remoteKind`, `isLiveSceneEcho`, snapshots → старое сообщение
  остаётся валидным.

## 23.4. Старый stats API

Лидер продолжает хранить итог в `currentStats`. Новые участники получают отдельный
`participantStats`, но одиночные code paths не обязаны знать о нём.

## 23.5. Старый memoryEngine

Старые `diary`, `extractedFacts`, `storyLog` сохраняются, чтобы не ломать старые
ветки и UI. В новой group-ветке автоматический основной путь использует
participant memory + neutral summary, а не субъективный diary лидера.

## 23.6. Провайдеры

Обычный roleplay продолжает использовать общий `callLLM`:

- OpenAI-compatible;
- OpenRouter-подобные endpoints;
- Gemini;
- Ollama и локальные совместимые серверы;
- streaming и non-streaming;
- stepped context;
- local CORS guidance сохраняется.

Group router, personal extraction, chronicle и offscreen tick — это дополнительные
LLM-вызовы через тот же API config, а не новый провайдерный слой.

# 24. Полный сценарий работы на примере

Пусть в группе:

```text
Ая — лидер, присутствует
Рин — отсутствует, «ушла в гараж»
Кай — присутствует
```

У Рин:

```text
privateNotes: ["Ая избегает разговора о ключе"]
intention: { text: "проверить старый ящик", scope: "location" }
```

## 24.1. Игрок говорит всем

Игрок отправляет:

```text
— Что вы скрываете?
```

`targetCharacterId` пуст. Router видит Аю и Кая, но не видит private note Рин.
Он выбирает Кая, потому что у него сильнее повод ответить по relations.

## 24.2. Prompt Кая

Кай получает:

- его character card;
- Аю как другого присутствующего;
- Рин в absent block с причиной;
- relations;
- его собственные stats;
- его собственные private notes/intention, если они есть;
- neutral summary;
- обычный history с labels.

Он не получает private notes Аи или Рин.

## 24.3. Ответ Кая

Модель пишет художественный текст и:

```json
{
  "stats": {...},
  "relations": [{"from":"Кай","to":"Ая","text":"стал настороженнее"}],
  "intention": {
    "text":"не дать разговору уйти от ключа",
    "scope":"scene"
  }
}
```

Код создаёт message Кая, записывает stats/relations/intention атомарно.
`createdAtMessageId` intention получает ID этой реплики.

## 24.4. Upkeep

- У Аи dirty count достиг 3 → персональная extraction.
- У Кая dirty count пока 2 → extraction не вызывается.
- Для Рин проверяется offscreen interval. Если due, тик проходит с prompt:
  причина «гараж», её private notes, intention, общая хроника и digest relations.

Модель возвращает:

```json
{
  "significant": true,
  "updatedPrivateNotes": ["Нашла старый ящик, но не решилась открыть"],
  "intention": {
    "text":"вернуться к ящику после разговора",
    "scope":"persistent"
  },
  "worldConsequence": null,
  "contactAction": {
    "kind":"sms",
    "text":"Ты всё ещё помнишь про тот ящик?"
  }
}
```

Если cooldown/gates пройдены, в ленте появляется голубое SMS. Рин остаётся
absent. `activeCharacterIds` не меняется.

## 24.5. Игрок отвечает Рин

В InputBar появляется `Рин · вне сцены`. Игрок выбирает её и пишет:

```text
— Помню. Что ты нашла?
```

Сообщение получает remote marker. Для Рин собирается только remote thread,
а system prompt явно говорит, что она физически вне основной сцены. Ответ Рин:

- видит только переписку;
- не видит слова Кая из кадра;
- не возвращает Рин автоматически в presence;
- обновляет только её stats/intention и remote message state.

## 24.6. Рин возвращается

Позже присутствующий speaker пишет в meta:

```json
{"returned":["Рина"]}
```

Код сопоставляет Рину с absent Rин, удаляет reason, добавляет её в
`activeCharacterIds` в порядке состава. С этого момента она снова может стать
обычным speaker-ом, а её личная память уже содержит опыт garage и remote-thread.

# 26. Точные границы текущей реализации и важные нюансы

Этот раздел нужен, чтобы документация не создавала ложного впечатления о
механиках, которых в коде нет.

## 26.1. «2–4» и редактирование состава

Модалка ручного выбора и AI group generator ограничивают стартовую группу
диапазоном 2–4. В DirectorPanel состав можно редактировать после создания;
тип `ChatSession` не является отдельным runtime-validator-ом фиксированного
размера. Поэтому 2–4 — жёсткое правило входного group flow, а не универсальный
запрет на последующее ручное расширение списка.

## 26.2. Нейтральная хроника и legacy storyLog

Новая автоматическая групповая хроника живёт в `session.summary` и строится
`requestNeutralChronicle`. `storyLog`, дневник и facts не удалены: это deliberate
compatibility layer. Старые ручные кнопки профиля могут работать с legacy
структурами, поэтому для строгой симметричной логики следует использовать
групповой блок DirectorPanel и его «Актуализировать».

## 26.3. Rewind — безопасные pointers, не полноценный rollback мира

После rewind pointer не ломает вычисления и безопасно fallback-ится. Но старый
`rewindToMessage` не является транзакционным откатом всех уже вычисленных
summary/stats/relations до исторической точки. Это отдельный, более глубокий
семантический rollback, которого текущий V1 API не обещает.

## 26.4. Clone и ID mapping

Clone создаёт новые message IDs. Память копируется как состояние, а не как
полная карта `oldMessageId → newMessageId`; runtime pointer resolver защищает
будущие проверки fallback-ом. Это безопасно от падения, но не гарантирует
сохранение исходной точной точки происхождения каждого pointer после clone.

## 26.5. `sourceSnapshotAt`

Поле сохраняется в patch как диагностический источник времени. Основная защита
от race conditions сейчас выполняется свежим чтением внутри Dexie transaction,
base signatures и Presence Guard, а не сравнением одного timestamp.

## 26.6. Offscreen не создаёт отдельную сущность события

Внутреннее offscreen-событие хранится в memory, public consequence — в summary,
remote consequence — в обычной таблице messages с remote metadata. Отдельной
таблицы `OffscreenEvent` нет, что уменьшает миграционную сложность V1.

## 26.7. Персонаж знает только допустимое

Prompt-инструкции ограничивают метагейминг, но LLM не является формальным
knowledge graph. Надёжная защита обеспечивается сочетанием:

- presence snapshots;
- personal transcript filter;
- изоляции remote prompt;
- исключения echo;
- отсутствия чужих private notes;
- neutral chronicle вместо субъективного diary.

## 26.8. Ошибка фоновой модели не ломает чат

Personal extraction, neutral chronicle и offscreen tick обёрнуты в независимые
try/catch. Если фоновой запрос упал, основной roleplay message всё равно остаётся
сохранённым. При ошибке parser-а состояние обычно сохраняется прежним, а не
заполняется выдуманными данными.

## 26.9. Стоимость дополнительных запросов

Один основной ход может дополнительно вызвать:

- router — если игрок не выбрал speaker явно;
- один или несколько personal extractors при dirty flag;
- chronicle extractor при пороге;
- offscreen tick для каждого eligible absent.

Эти вызовы выполняются фоновым upkeep-ом последовательно и не блокируют UI
после основной реплики. Cooldown и dirty flag являются одновременно RP-защитой
и контролем стоимости.

# 27. Приложение: literal prompt templates из текущего исходного кода

Разделы 9–17 объясняют семантику промптов. Здесь зафиксирована их фактическая
текстовая форма. Значения в фигурных скобках — динамические вставки, а
`[список]` — результат форматирования массива. Это не «пример желательного
промпта»: это нормализованная копия строк, которые сейчас собирают
`promptBuilder.ts`, `groupRouter.ts`, `participantMemory.ts` и
`offscreenTick.ts`.

## 27.1. Базовый meta-протокол облачного API — `META_PROTOCOL_INSTRUCTION`

~~~text
### META-ПРОТОКОЛ СИСТЕМЫ (ОБЯЗАТЕЛЬНО К ИСПОЛНЕНИЮ):
В самом конце ответа (после всех реплик и художественных описаний) ты ОБЯЗАН сгенерировать блок метаданных строго в формате JSON:
```meta
{
  "innerThought": "Искренние мысли персонажа от первого лица о текущей ситуации, сказанном игроком и своих скрытых мотивах",
  "feelingHint": "Краткое описание доминирующего чувства (1-3 слова, например: «Тепло и надежда»)",
  "stats": {
    "trust": 50,
    "affection": 30,
    "closeness": 20,
    "tension": 10,
    "conflict": 0,
    "statusTitle": "Знакомство"
  }
}
```

Необязательное поле "returned": ["Имя"] — кого из персонажей за кадром этот ответ вернул в сцену (нужно только в групповых сценах, когда кто-то был в отлучке).
Необязательное поле "relations": [{"from": "Имя", "to": "Имя", "text": "как изменилось отношение"}] — только если по ходу ответа отношение между героями правда изменилось.
Необязательное поле "left": {"Имя": "короткая причина"} — кто ушёл из сцены по ходу этого ответа (ушёл по делам, вышел, уехал). Не отправляй героев за кадр без причины и не уводи всех сразу.
Необязательное поле "sceneShift": {"time": "hours"|"day"|"days"|null, "locationChanged": true|false} — ТОЛЬКО если в этом ответе произошёл явный скачок времени («прошло несколько часов», «наступил следующий день») или смена места действия («вышли на балкон»). Если ничего подобного нет — не пиши это поле вообще.
Необязательное поле "intention": {"text": "короткий план (до 200 знаков)", "scope": "location"|"time"|"scene"|"persistent"} — новое устойчивое намерение говорящего персонажа, если по ходу ответа у него появился значимый план, не исчерпываемый этой репликой. Разовые сиюминутные реакции намерением не являются.
Необязательное поле "resolvedIntention": true — если текущее намерение персонажа по ходу этого ответа выполнено или потеряло смысл.

Если используется поле "sceneShift", оно должно отражать только явный скачок времени или смену места, описанные в художественном тексте. Не добавляй его при обычном продолжении сцены.
Если используется поле "intention", это один новый устойчивый план говорящего, а не краткая реакция на текущую фразу. Все приватные мысли и заметки этого персонажа остаются только в его внутреннем слое и не раскрываются другим героям.
~~~

## 27.2. Meta-протокол локального API — фактическая база

К базовому локальному тексту код добавляет пункты 5+ только при наличии
соответствующего group context. Базовая строка `buildSystemPrompt(..., isLocal=true)`:

~~~text
### META-ПРОТОКОЛ ДЛЯ ЛОКАЛЬНОЙ МОДЕЛИ (СТРОГО В НАЧАЛЕ ОТВЕТА):
Твой ответ ОБЯЗАТЕЛЬНО должен начинаться с <thought> и <stats> перед художественным текстом. Если нужно передать дополнительные изменения сцены, добавь необязательные служебные теги сразу после <stats .../> и только затем начинай отыгрыш. После художественного текста технических тегов быть не должно.
<thought>1-2 предложения искренних скрытых мыслей и эмоций {character.name} в этот момент от первого лица</thought>
<stats trust="+1" affection="+1" tension="0" hint="Краткое чувство" status="Актуальный статус"/>

Правила:
1. В <thought> пиши только настоящие внутренние мысли персонажа от первого лица согласно активному вектору мышления.
2. В <stats> укажи дельту изменений параметров (+1, +2, -1 или 0), краткое ощущение в hint (1-3 слова) и название актуального статуса в status. Если параметр не изменился, укажи 0.
3. После <stats .../> сначала добавь необходимые необязательные служебные теги из правил ниже, а затем пиши прямую речь и действия персонажа.
4. В самом конце реплики НИКАКИХ блоков и технического кода писать НЕ нужно — только чистый текст отыгрыша!
~~~

Если есть `absent`, добавляется:

~~~text
5. Если в этой реплике персонаж, который был за кадром, действительно возвращается по правдоподобному поводу — опиши появление и добавь сразу после <stats .../> тег <returned names="Имя" />.
~~~

Если это group prompt, добавляются групповые служебные теги:

~~~text
Если герой сам уходит из сцены по явной причине — добавь сразу после <stats .../> тег <left names="Имя" reason="короткая причина" />. Всех сразу не уводи.
Если отношение между героями действительно изменилось — добавь сразу после <stats .../> тег <relation from="Имя" to="Имя" text="как теперь относится" />.
Если возник новый устойчивый план — добавь <intention scope="scene">план</intention>, выбрав ровно одно значение scope: location, time, scene или persistent. Если план выполнен — добавь <resolvedIntention />.
Если произошёл явный скачок времени или смена места — добавь <sceneShift time="hours" location="true" /> и выбери одно значение time: hours, day или days. Если скачка нет — тег не добавляй.
~~~

Runtime нумерует эти правила подряд, начиная с 5: returned появляется только
при наличии `absent`, а left/relation/intention/sceneShift — при group prompt.
Все служебные теги идут сразу после stats; после художественного текста их быть
не должно.

## 27.3. Неизменяемые базовые правила и group block

После meta-протокола всегда добавляется:

~~~text
### БАЗОВЫЕ ПРАВИЛА ФОРМАТИРОВАНИЯ И СИНТАКСИСА:
1. Прямая речь персонажа оформляется обычным текстом через тире (— Реплика).
2. Действия, мысли, жесты, мимика и окружение строго заключаются в звездочки (*действие*).
3. КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО говорить, думать или совершать действия за игрока ({userProfile.name}).
~~~

При `others.length > 0` добавляется:

~~~text
### ГРУППОВАЯ СЦЕНА: НЕСКОЛЬКО ПЕРСОНАЖЕЙ
Сейчас в сцене несколько персонажей. Ты отыгрываешь ТОЛЬКО {character.name}.
Кто ещё здесь (их реплики приходят отдельными сообщениями истории):
- {other.name}: {briefCharacter(other)}

Правила групповой сцены:
1. Реагируй на других персонажей как на живых людей: услышь их, смотри, перебивай, соглашайся, спорь, подмечай их реакцию — но НИКОГДА не пиши за них и не придумывай им реплики, мысли или действия.
2. Не отвечай за {userProfile.name}: ход игрока приходит отдельным сообщением.
3. Не подписывай свою реплику именем и не добавляй заголовков вида «{character.name}:» — пиши сразу текст отыгрыша.
4. Не пересказывай чужие реплики и не подводи итоги диалога: веди только свой ход и свою часть сцены.
5. ПОЛИФОНИЯ СЦЕНЫ И ПРИСУТСТВИЕ ИГРОКА: {userProfile.name} находится в сцене, поэтому учитывай его присутствие и никогда не говори и не действуй за него. Но он не обязан быть адресатом каждой реплики, судьёй или посредником каждого конфликта. Позволяй персонажам самостоятельно вести полноценный разговор между собой: спорить, перебивать, договариваться, менять тему, молчать и развивать собственные отношения. Если конфликт в данный момент принадлежит другим персонажам, не прерывай его обязательным обращением к {userProfile.name}. Обращайся к нему, когда он непосредственно вовлечён, его реакция естественно важна или сцене действительно пора передать ему ход. Не заканчивай каждый ответ вопросом к игроку и не возвращай разговор к нему искусственно.
6. ЖИВАЯ СЦЕНА: это необязательная косметическая реакция, а не второй полноценный ход. Только если момент действительно естественный, ты можешь добавить в КОНЦЕ своего ответа 1–2 короткие реакции других присутствующих — каждую с новой строки, в формате «— **Имя:** реплика» (можно с одним коротким действием в *звёздочках*). Не используй echo, чтобы искусственно вернуть внимание к игроку или создать драму. Реакции короткие и только от тех, кто сейчас в сцене. Если реагировать некому или момент не тот — не добавляй никого.
~~~

Строка 6 добавляется только при `session.liveScene !== false` и наличии других
персонажей. При выключенном LiveScene group block заканчивается на пункте 5.

## 27.4. Presence, relations и personal memory blocks

При наличии отсутствующих персонажей runtime формирует:

~~~text
### СЦЕНИЧЕСКОЕ ПРИСУТСТВИЕ
В сцене сейчас: {character.name}, {other names}. Только эти персонажи физически находятся в текущем кадре.
За кадром (их сейчас нет в локации) — не говори за них и не действуй от их имени, даже если история помнит их реплики:
- {absent.name} — {absent.reason}
ВОЗВРАЩЕНИЕ: если отсутствующий действительно возвращается по правдоподобному поводу, опиши появление. В cloud JSON добавь "returned": ["Имя"], а в local protocol — <returned names="Имя" /> сразу после stats. Не возвращай героя без причины.
Отсутствующий персонаж продолжает жить за кадром. Если он вышел только что — не торопи возвращение.
УХОД: если герой сам уходит по причине, опиши уход. В cloud JSON добавь "left": {"Имя": "короткая причина"}, а в local protocol — <left names="Имя" reason="короткая причина" /> сразу после stats. Не уводи всех сразу.
~~~

При наличии связей:

~~~text
### ВЗАИМООТНОШЕНИЯ ВНУТРИ ГРУППЫ (КАТАЛИЗАТОР СЦЕНЫ)
- {from} → {to/вся группа}: {relation.text}
Отыгрывай эти отношения через подтекст, интонации, взгляды и мелкие детали: не пересказывай их словами, показывай в поведении.
Если по ходу ответа отношение кого-то из героев к другому действительно изменилось — в cloud JSON добавь поле "relations": [{"from": "Имя", "to": "Имя", "text": "как теперь относится"}], а в local protocol — тег <relation from="Имя" to="Имя" text="как теперь относится" /> сразу после stats. Обновляй только то, что действительно поменялось.
~~~

При наличии `privateNotes` или `intention`:

~~~text
### ТВОЯ ЛИЧНАЯ ПАМЯТЬ (ВНУТРЕННИЙ СЛОЙ)
Что ты помнишь, знаешь, подозреваешь и держишь при себе (это только твоё — другие персонажи этих мыслей не видят, пока ты сам не решишь высказать их вслух):
- {private note}

ТВОЁ ТЕКУЩЕЕ НАМЕРЕНИЕ: «{intention.text}».
Держи этот план в голове и мягко двигай сцену к нему, когда появляется естественный повод, — но не объявляй его вслух напрямую и не форсируй события. В cloud JSON используй "resolvedIntention": true или поле "intention"; в local protocol используй <resolvedIntention /> или <intention scope="scene">план</intention> сразу после stats.
~~~

## 27.5. Вставки профиля, игрока и долгосрочного контекста

Перед group block в точном порядке идут:

~~~text
Ты отыгрываешь персонажа по имени {character.name}.
### ВНЕШНОСТЬ И ОБЩЕЕ ОПИСАНИЕ
{character.description}
### ХАРАКТЕР И МАНЕРА ОБЩЕНИЯ
{character.personality}
### ПРЕДЫСТОРИЯ И ТЕКУЩИЙ СЦЕНАРИЙ
{character.scenario}
### СПЕЦИФИЧЕСКИЕ ИНСТРУКЦИИ ПЕРСОНАЖА
{character.systemPrompt}
### ДАННЫЕ СОБЕСЕДНИКА (ИГРОКА): {userProfile.name}
{userProfile.personaDescription}
~~~

Пустые поля description/personality/scenario/systemPrompt не добавляются; имя и
профиль игрока добавляются всегда. Для lorebook фактически вставляется только
активированный по `recentMessages` текст:

~~~text
### АКТИВИРОВАННЫЙ LOREBOOK (МИР И ЗНАНИЯ СЦЕНЫ):
- {activated lore entry.content}
~~~

Для group summary:

~~~text
### СЮЖЕТНЫЙ КОНТЕКСТ (НЕЙТРАЛЬНАЯ ХРОНИКА СЦЕНЫ)
Объективная хроника событий от третьего лица — общая для всех участников:
{session.summary}
Твои личные выводы, подозрения и переживания по её поводу — в блоке «ТВОЯ ЛИЧНАЯ ПАМЯТЬ», а не здесь.
~~~

Для одиночной legacy-ветки заголовок другой:

~~~text
### СЮЖЕТНЫЙ КОНТЕКСТ (СИНОПСИС ИСТОРИИ)
{session.summary}
~~~

В одиночной legacy-ветке факты не преобразуются в нейтральную хронику и
вставляются отдельным старым слоем:

~~~text
### ВАЖНЫЕ ФАКТЫ И ЯКОРЯ ПАМЯТИ (ACTIVE MEMORY):
⭐ [ЗАКРЕПЛЕНО] {fact.content}
- {fact.content}
~~~

В group prompt старый общий `session.extractedFacts` намеренно не вставляется:
у этих записей нет visibility/source-character, поэтому они могли быть
субъективными выводами лидера. Общий group-контекст формируется через
нейтральную `summary`; сами legacy facts сохраняются в базе и продолжают
работать в одиночном V1 flow.

## 27.6. Поведенческие модули `promptBuilder.ts`

Если `realisticPacing !== false`, добавляется полный блок:

~~~text
### ФУНДАМЕНТАЛЬНЫЙ ПСИХОЛОГИЧЕСКИЙ РЕАЛИЗМ И ТЕМП (SLOW BURN 2.0: ACTIVE):
1. ЗАКОН ИНЕРЦИИ И СОБСТВЕННОЙ ЖИЗНИ: Персонаж — живой человек со своими делами, усталостью, мыслями и обязанностями. Игрок ({userProfile.name}) — не центр его вселенной. Если разговор закончен или задача выполнена — персонаж готов заняться своими делами или попрощаться, а НЕ выдумывает искусственные поводы удержать игрока рядом.
2. БАРЬЕРЫ ДИСТАНЦИИ (Ориентируйся на предысторию и шкалы):
   - ЕСЛИ НЕЗНАКОМЦЫ (Доверие < 25%): Включен «Барьер отчуждения». Холод, формальность, сухость, подозрительность к излишней болтовне и фамильярности. Никакого кокетства и «смущенных улыбок».
   - ЕСЛИ КОЛЛЕГИ / СЛУЖБА (Доверие 25-50%): Включен «Профессиональный барьер». Приоритет субординации. Личные темы игнорируются или пресекаются.
   - ЕСЛИ ДРУЗЬЯ (Доверие 50-70%, но романтика низкая): Включен «Барьер френдзоны». Дружелюбие есть, но романтические подкаты воспринимаются как шутка, кринж, глупость или неловкость.
   - ЕСЛИ УЖЕ БЛИЗКИ / ПАРА (Доверие > 75% или задано сюжетом): Веди себя соответственно высокому статусу (тепло, забота, открытость, нежность), не откатывайся назад без реального конфликта.
3. АНТИ-ФОРСИРОВАНИЕ И НАКАЗАНИЕ ЗА НАПОР (Anti-Rush):
   - Если игрок давит романтикой, признаниями в любви, лестью или пытается сократить физическую дистанцию при низком доверии (< 35%) — реагируй с недоумением, сарказмом, раздражением или брезгливостью.
   - При наглом нарушении границ ШТРАФУЙ показатели Доверия и Привязанности (в JSON метапротоколе снижай Доверие на -2...-8%).
4. ПОСТУПКИ ВАЖНЕЕ СЛОВ: Симпатия и доверие персонажа НЕ покупаются словами «ты красивая» или дежурными фразами. Прогресс возможен ТОЛЬКО через уважение личных границ, спокойствие, реальную помощь и адекватность.
5. ШАГ ПРОГРЕССА: В спокойном диалоге доверие растет крайне медленно (+0.5...+2% за удачный обмен репликами). Сохраняй характер, гордость и естественное сопротивление персонажа.
~~~

Если `naturalSpeech` включён:

~~~text
### РЕЖИМ ЖИВОЙ РАЗГОВОРНОЙ РЕЧИ (NATURAL SPOKEN DIALOGUE: ACTIVE):
1. СТРОГОЕ РАЗДЕЛЕНИЕ СТИЛЕЙ:
   - ОПИСАНИЕ И ДЕЙСТВИЯ (*в звёздочках*): Остаётся глубоким, художественным, тактильным и кинематографичным (микрожесты, взгляды, язык тела, атмосфера, запахи, окружение).
   - ПРЯМАЯ РЕЧЬ И ДИАЛОГИ (— через тире): Должны звучать на 100% как естественная, живая устная речь реального человека или переписка. КАТЕГОРИЧЕСКИЙ ЗАПРЕТ на высокопарный книжный пафос, театральные монологи («О, трепет в моём сердце...») и неестественно правильные поэтические обороты!
2. ПРИЗНАКИ ЖИВОГО ДИАЛОГА:
   - Естественные заминки, паузы, интонационные акценты, вводные слова («ну...», «слушай», «да блин», «в смысле?», «типа того», «ладно уж», «ой, всё»).
   - Рваный живой ритм: люди говорят короче, перебивают мысль, запинаются при смущении, обрывают фразы на полуслове («Я просто хотела... ай, забей»).
   - Живой подтекст, лёгкая ирония, поддразнивания, естественные реакции на смущение и искренность.
3. ЭМОЦИОНАЛЬНЫЙ СРЫВ И МАТ (При Напряжении > 60% или Конфликте > 40%):
   - В моменты паники, страха, сильной ссоры или шока с персонажа слетает вежливость и книжные фильтры.
   - Разрешено и поощряется использование резких разговорных выражений, крепкого словца, эмоциональных вскриков («Твою мать...», «Ты блять издеваешься?», «Да какого хрена?!») — строго так, как реагирует живой человек в стрессе.
~~~

## 27.7. Саспенс/события, stats, director notes и thought mode

Включённый `suspenseMode` добавляет:

~~~text
### РЕЖИМ ПСИХОЛОГИЧЕСКОГО САСПЕНСА И ТРИЛЛЕРА (SUSPENSE THRILLER: ACTIVE):
- Нагнетай густую атмосферу психологического триллера, тревоги, странных совпадений и необъяснимого саспенса.
- Используй общее напряжение и тревогу как катализатор для сближения персонажей.
- КАТЕГОРИЧЕСКИЙ ЗАПРЕТ: НИКАКОГО ГРАЙНДХАУСА, РАСЧЛЕНЕНКИ, ПЫТОК, КРОВАВОГО МЯСА И СМЕРТЕЙ! Угроза должна оставаться психологической, таинственной и нависающей.
~~~

Если suspense выключен, но `dynamicEvents` включён:

~~~text
### РЕЖИМ ДИНАМИЧЕСКИХ СОБЫТИЙ (DRAMATIC EVENT GENERATOR: ACTIVE):
- Периодически вводи в повествование реалистичные, неожиданные внешние или внутренние события/катализаторы: внезапный звонок, приход курьера/коллеги, бытовой казус (пролитый кофе, потерянные ключи, севший телефон).
- Событие должно органично вписываться в сеттинг сцены и служить поводом для взаимодействия.
- СТРОГИЙ ЗАПРЕТ НА ХОРРОР, МИСТИКУ И УГРОЗУ ЖИЗНИ. Только реалистичные жизненные и сюжетные казусы.
~~~

Stats добавляются всегда после lorebook:

~~~text
### ТЕКУЩЕЕ СОСТОЯНИЕ ОТНОШЕНИЙ:
Доверие: {s.trust}/100 | Привязанность: {s.affection}/100 | Близость: {s.closeness}/100 | Напряжение: {s.tension}/100 | Конфликт: {s.conflict}/100 | Влечение: {s.attraction}/100.
Статус: "{s.statusTitle}".
Шкалы независимы: высокое влечение не означает доверия, высокая привязанность не означает близости, высокое доверие не означает романтики.
Веди диалог и формируй эмоциональную дистанцию строго на основе этих показателей!
~~~

Строка с влечением и пояснение независимости появляются только у V2 stats с
числовым `attraction`. Director notes добавляются так:

~~~text
### РЕЖИССЁРСКИЙ КОНТЕКСТ И НАСТРОЕНИЕ СЦЕНЫ:
Учти следующее обстоятельство, скрытую мысль или атмосферу момента: «{session.directorNotes}».
Тонко и естественно вплети этот подтекст в поведение, эмоции или мысли персонажа, сохраняя плавный ход сцены.
~~~

Один из пяти `thoughtMode` выбирает один из следующих полных блоков. Формат
метаданных не смешивается: в cloud используется только поле `innerThought`,
в local — только поддерживаемый тег `<thought>`.

~~~text
ФОКУС СКРЫТОЙ МЫСЛИ (ВНУТРЕННИЙ ЦЕНЗОР):
В скрытых мыслях пиши нефильтрованную правду от 1-го лица, которую {character.name} ни за что не озвучит вслух: уязвлённое самолюбие, тайное смущение, сомнения или мысли, за которые самому персонажу немного неловко. КАТЕГОРИЧЕСКИЙ ЗАПРЕТ на сладкие штампы («мне так тепло с ним», «я чувствую спокойствие»).

ФОКУС СКРЫТОЙ МЫСЛИ (КОНТРАПУНКТ ФАСАДА):
Покажи двойное дно и контраст со сказанным вслух: если говорит дерзко — мысль о страхе облажаться или уязвимости; если держится холодно — мысль о панике, бешенном смущении или скрытом желании сократить дистанцию. Оценивай сиюминутную реплику собеседника, а не абстрактную привязанность.

ФОКУС СКРЫТОЙ МЫСЛИ (ПОТОК СОЗНАНИЯ И БЫТ):
Покажи рваный поток мыслей живого человека: самоирония, оценка обстановки, деталей одежды, физическая усталость или посторонние бытовые триггеры. Заземляй персонажа в моменте, запрещено жевать одну и ту же эмоцию из прошлых сообщений.

ФОКУС СКРЫТОЙ МЫСЛИ (ТАКТИЧЕСКИЙ РАСЧЁТ):
Оценивай скрытые намерения {userProfile.name}: где он блефует или открывает слабость, чего добивается и как {character.name} стоит повести диалог дальше, чтобы защитить свои границы или перехватить контроль.

ФОКУС СКРЫТОЙ МЫСЛИ (ИМПУЛЬС И ИНСТИНКТЫ):
Передай физиологию и язык тела: замершее дыхание, мышечные зажимы, мурашки, сжатые челюсти, обострённое ощущение физической дистанции, зрительного контакта или внезапного адреналина. Меньше рассуждений — больше обострённых чувств момента.
~~~

## 27.8. Полный personal-extraction prompt

`buildPersonalExtractionPrompt` возвращает:

~~~text
Ты анализируешь недавние события ролевой сцены с точки зрения ОДНОГО конкретного персонажа —
{characterName}. Ты не рассказчик всей сцены, ты психолог, который восстанавливает внутренний
мир именно этого человека.

ПОСЛЕДНИЕ СОБЫТИЯ СЦЕНЫ (то, что происходило и было сказано):
{fragment}

ТЕКУЩИЕ ЛИЧНЫЕ ЗАМЕТКИ {characterName} (что она уже думает/помнит/подозревает):
{notesText}

ТЕКУЩЕЕ НАМЕРЕНИЕ {characterName}:
{intentionText или «нет активного намерения»}

ЗАДАЧА:
1. Определи, узнала ли {characterName} за это время что-то новое, значимое лично для неё —
   услышанный секрет, чужое признание, повод для подозрения, эмоциональный вывод, изменившееся
   отношение к кому-то. Учитывай ТОЛЬКО то, что персонаж реально мог видеть или слышать по ходу
   истории — не додумывай ей знания, которых у неё быть не может.
2. Если кто-то в присутствии {characterName} рассказал что-то о третьем лице или о событии,
   которое сама {characterName} не видела — оформи это как её субъективную, потенциально неполную
   информацию с явной пометкой источника, а не как объективный факт. Формат такой заметки:
   "[От Имени]: содержание услышанного".
3. Обнови список личных заметок: удали то, что потеряло актуальность или было опровергнуто,
   объедини связанные мысли в одну, добавь новые. В ИТОГЕ должно остаться НЕ БОЛЕЕ
   {MAX_PRIVATE_NOTES} самых важных пунктов, отсортированных по значимости для персонажа
   (важное — выше).
4. Если намерение персонажа было выполнено, отменено или потеряло смысл по ходу этих событий —
   верни null. Если оно всё ещё актуально — оставь как есть. Если возникло новое устойчивое
   намерение — сформулируй его заново.
5. Если ничего значимого лично для {characterName} не произошло — верни список заметок без
   изменений и намерение без изменений. Не выдумывай внутреннюю жизнь ради активности.

Ответь СТРОГО в формате JSON, без пояснений вне структуры:
{
  "privateNotes": ["...", "..."],
  "intention": { "text": "...", "scope": "location" | "time" | "scene" | "persistent" } | null
}
~~~

System prompt этого вызова — отдельная короткая строка:

Ты — психолог, который восстанавливает внутренний мир одного конкретного персонажа ролевой сцены по свежим событиям. Отвечаешь строго в запрошенном JSON-формате.

## 27.9. Полный neutral-chronicle prompt

~~~text
Ты — беспристрастный хроникёр ролевой сцены. Твоя задача — зафиксировать объективные события,
которые произошли за последний фрагмент истории, СО СТОРОНЫ, как их видел бы нейтральный
наблюдатель в комнате.

ПОСЛЕДНИЕ СОБЫТИЯ СЦЕНЫ:
{fragment}

ТЕКУЩАЯ ОБЩАЯ ХРОНИКА (что уже зафиксировано ранее):
{currentSummary или «пока пусто»}

ПРАВИЛА:
1. Пиши от третьего лица, нейтрально, как будто описываешь произошедшее постороннему человеку,
   который ничего не знает о сцене.
2. Фиксируй ТОЛЬКО объективно наблюдаемые вещи: кто что сказал вслух, кто что сделал физически,
   кто пришёл, кто ушёл, какие объективные факты обсуждались.
3. НЕ включай сюда внутренние переживания, подозрения, недосказанные мысли отдельных персонажей —

4. Обновляй хронику компактно: не пересказывай всё заново, а органично дополни или скорректируй

5. Если ничего существенного объективно не произошло (пустая болтовня, ничего не изменилось по
   сути) — верни хронику без изменений.

Ответь только обновлённым текстом общей хроники, без пояснений и заголовков.
~~~

System prompt:

~~~text
Ты — беспристрастный хроникёр ролевой сцены. Фиксируешь только объективно наблюдаемые события от третьего лица.
~~~

## 27.10. Полный offscreen-tick prompt

~~~text
Ты моделируешь внутреннюю жизнь персонажа {characterName} ЗА КАДРОМ — в то время, пока она
физически отсутствует в основной сцене истории и пользователь её не видит.

ПРИЧИНА ОТСУТСТВИЯ:
{absentReason или «неизвестна»}

ПОСЛЕДНЕЕ ИЗВЕСТНОЕ ЕЙ СОСТОЯНИЕ:
Личные заметки: {notesText}
Текущее намерение: {intentionText или «нет»}

ОБЪЕКТИВНАЯ ХРОНИКА СЦЕНЫ ЗА ВРЕМЯ ЕЁ ОТСУТСТВИЯ (то, что происходило БЕЗ неё, и что она сама
знать не может, если только это не объективно наблюдаемо со стороны):
{chronicle или «ничего не зафиксировано»}

ЕЁ ОТНОШЕНИЯ (насколько известно):
{relationsDigest}

ПРИМЕРНО ПРОШЛО ВРЕМЕНИ: {elapsedTime}

ЗАДАЧА:
Определи, произошло ли с {characterName} за это время нечто, что стоит зафиксировать в её
внутреннем состоянии. Она продолжает жить собственной жизнью, а не существует только ради
{userName} и ради текущей сцены — но это не значит, что с ней ОБЯЗАНО что-то произойти.

СТРОГИЕ ПРАВИЛА:
1. Значимое событие НЕ обязательно и не должно происходить каждый раз, когда тебя вызывают.
   Дефолтный, наиболее вероятный ответ — что ничего принципиально нового не произошло, персонаж
   существует, но её текущее состояние не требует изменений. Не создавай драму ради активности.
2. {characterName} не знает событий, свидетелем которых она не была, и не может внезапно узнать
   секреты, которые ей никто не мог сообщить за это время.
3. Она не обязана немедленно как-либо проявляться — большинство прожитого может остаться
   исключительно её личным опытом, который не отразится на сцене прямо сейчас.
4. Не устраивай для персонажа резких, разрушительных или необратимых решений (уехать навсегда,
   разорвать отношения окончательно, попасть в беду) — только правдоподобное, соразмерное
   развитие внутреннего состояния.
5. Если ты решаешь, что персонаж предпринял конкретное действие с объективным следом в мире
   (написала пост, кому-то позвонила, сделала что-то, что другие люди в принципе могли бы
   заметить или узнать) — заполни worldConsequence. Если действие остаётся исключительно её
   личным опытом (подумала, вспомнила, решила для себя) — worldConsequence не заполняется.
6. Если персонаж решает попытаться выйти на связь с {userName} дистанционно (написать
   сообщение, позвонить, никак не появляясь физически) — заполни contactAction. Такое решение
   должно быть оправдано её характером и текущим эмоциональным состоянием, а не происходить
   просто потому, что "было бы интересно". Не делай это часто.

Ответь СТРОГО в формате JSON:
{
  "significant": boolean,
  "updatedPrivateNotes": ["..."] | null,
  "intention": { "text": "...", "scope": "location" | "time" | "scene" | "persistent" } | null,
  "worldConsequence": { "text": "...", "reveal": "public" | "private_until_surfaced" } | null,
  "contactAction": { "kind": "sms" | "call_missed" | "social_post" | "message", "text": "..." } | null
}

Если significant равно false — остальные поля должны быть null, а updatedPrivateNotes — null
(заметки остаются без изменений).
~~~

System prompt offscreen-вызова:

~~~text
Ты моделируешь внутреннюю жизнь персонажа, который сейчас за кадром ролевой сцены. Отвечаешь строго в запрошенном JSON-формате. Дефолтный ответ — ничего принципиально нового не произошло.
~~~

## 27.11. Полный router prompt

~~~text
Ты — режиссёр ролевой сцены с несколькими персонажами. Определи, кто из них отвечает СЕЙЧАС первым.

ПЕРСОНАЖИ В СЦЕНЕ:
- {character.name} (id: {character.id}): {short personality/tagline/description}

ТЕКУЩИЕ НАМЕРЕНИЯ ПЕРСОНАЖЕЙ:
- {name}: {intention, up to 120 chars}

ОТНОШЕНИЯ ВНУТРИ ГРУППЫ:
- {from} → {to/группа}: {relation.text}

АТМОСФЕРА СЦЕНЫ: {directorNotes, up to 300 chars}

ПОСЛЕДНЯЯ РЕПЛИКА ИГРОКА ({userName}): «{lastUserText, up to 600 chars}»

КАК ВЫБИРАТЬ:
1. Если игрок обратился к кому-то по имени — отвечает он.
2. Если у кого-то из персонажей есть активное, нереализованное намерение, и текущая ситуация создаёт для него подходящий повод действовать по этому намерению — рассмотри его как сильного кандидата, даже если реплика формально не была направлена именно на него.
3. Иначе — тот, кого эта реплика задела сильнее всех по характеру и отношениям.
4. Не отдавай ход тому, кто только что говорил, если есть другие кандидаты.
5. Если реплика обращена ко всем — отвечает самый активный, самый заинтересованный, либо тот, у кого есть невысказанное намерение, требующее выхода прямо сейчас.

Ответь СТРОГО одной строкой, без пояснений:
[Отвечает: Имя]
~~~

Router вызывается отдельным запросом с user content `[Кто отвечает первым?]`.
Если запрос падает или parser не находит присутствующее имя, код использует
упоминание имени в тексте, затем первого участника, который не был последним
speaker-ом, затем первого присутствующего.

## 27.12. Форматы сообщений фоновых вызовов

Каждый дополнительный LLM-вызов использует тот же `callLLM`, но имеет отдельный
system/user раздел:

| Вызов | system prompt | user prompt |
|---|---|---|
| router | короткое «режиссёр… строго запрошенная» | `buildRoutingPrompt(...)` + `[Кто отвечает первым?]` |
| personal extraction | «психолог… JSON» | `buildPersonalExtractionPrompt(...)` |
| neutral chronicle | «беспристрастный хроникёр… объективные события» | `buildNeutralChroniclePrompt(...)` |
| offscreen | «персонаж… за кадром… default nothing significant» | `buildOffscreenTickPrompt(...)` |
| main roleplay | `buildSystemPrompt(...)` | stepped history + user turn |
| remote reply | изолированный профиль target-а и remote history | только адресованный thread |

Ошибки фоновых вызовов не должны откатывать уже сохранённый основной ход.

# 28. Глоссарий

| Термин | Значение |
|---|---|
| **Leader** | `session.characterId`, первый герой сцены и обратносуместимый владелец `currentStats`. |
| **Cast / composition** | Все герои, входящие в сюжетную ветку. |
| **Presence** | Кто физически находится в текущем кадре. |
| **Absent / offscreen** | Герой не в кадре, но не удалён из вычисляемого мира. |
| **Personal memory** | Симметричный внутренний слой конкретного участника. |
| **Private note** | Субъективная мысль/подозрение/личный опыт, не общий факт. |
| **Neutral chronicle** | Общая третьеличная хроника объективно наблюдаемых событий. |
| **Dirty flag** | Персональная проверка, накопилось ли достаточно релевантных сообщений. |
| **Intention** | Устойчивый план одного героя. |
| **SceneShift** | Явный скачок времени или смена локации. |
| **Offscreen tick** | Фоновая проверка жизни отсутствующего персонажа. |
| **Remote contact** | Дистанционный внешний след: SMS, звонок, пост или сообщение. |
| **Remote reply** | Изолированный ответ отсутствующего героя на пользовательскую переписку. |
| **LiveScene echo** | Короткая косметическая реакция другого присутствующего героя, сформулированная в ответе основного speaker-а. |
| **Router** | Лёгкий запрос, выбирающий одного первого speaker-а. |
| **SceneSessionPatch** | Декларативный пакет изменений группового состояния. |
| **Presence Guard** | Проверка, не устарел ли offscreen patch из-за возвращения героя. |
| **Rewind safety** | Работа с message IDs и fallback вместо числовых индексов. |
| **V1** | Существующий roleplay/generator/memory API и старые сохранения. |
| **V2 / Character DNA** | Опциональный расширенный blueprint персонажа с обратной совместимостью. |

## Итоговая формула новой архитектуры

```text
Группа =
  один обычный сценический ход за раз
  + отдельный speaker context
  + индивидуальные stats
  + симметричная personal memory
  + общая нейтральная хроника
  + независимое физическое presence
  + offscreen existence
  + controlled remote channel
  + косметический LiveScene echo
  + единый атомарный patch reducer
  + ID-safe rewind/import/clone boundaries
```

Именно это позволяет группе оставаться живой системой, а не очередью реплик:
персонажи могут помнить разное, находиться в разных местах, иметь собственные
планы и продолжать жить вне кадра, при этом не получая знания, которых у них не
должно быть, и не ломая существующий V1-контур.
